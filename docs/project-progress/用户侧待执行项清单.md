## F1 · Flyway ECS 基线演练与登记核验（簇⑥ 批1a，v2.54）

**目的**：现网库接入 Flyway 迁移版本化前的受控演练（4.11 验收组成：DB 迁移版本化 100% 的第一步）。机制 = `baseline-on-migrate=true + baseline-version=0`：非空现网库首跑插 baseline 登记行，V1 脚本全 `IF NOT EXISTS` 幂等零结构变更。

**前置**：
- 含 v2.54 Flyway 的构建产物已就绪（本地 `mvn -q -DskipTests package` 出的 fat jar，或已随批1b 镜像）；
- ECS 宿主可直连 PG（PG 为宿主原生安装，`psql` 可用）；
- 配置无需额外环境变量（缺省即 baseline 策略；`FLYWAY_ENABLED` 缺省 true）。

**步骤**：

1. ⚠️ **先备份现网库**（宿主执行，留档勿删）：
   ```bash
   pg_dump -Fc -h 127.0.0.1 -U <db_user> kb_rag_agent > /tmp/kb_rag_agent_$(date +%F).dump
   ls -la /tmp/kb_rag_agent_*.dump   # 确认非空
   ```
2. **建演练库并恢复**：
   ```bash
   createdb -h 127.0.0.1 -U <db_user> kb_rag_agent_flyway_drill
   pg_restore -h 127.0.0.1 -U <db_user> -d kb_rag_agent_flyway_drill /tmp/kb_rag_agent_$(date +%F).dump
   ```
3. **kb-api 指向演练库启动一次**（两形态任选）：
   - fat jar 直起：
     ```bash
     export DB_URL='jdbc:postgresql://127.0.0.1:5432/kb_rag_agent_flyway_drill'
     export DB_USERNAME=<db_user> DB_PASSWORD=<密码>
     java --enable-preview -jar kb-api/target/kb-api-1.0.0-SNAPSHOT.jar 2>&1 | tee /tmp/flyway-drill.log
     ```
   - 容器形态（F3 已做时）：临时改 `infra/.env` 的 `DB_URL` 为 `jdbc:postgresql://host.docker.internal:5432/kb_rag_agent_flyway_drill` → `cd infra && docker compose -f docker-compose.app.yml up -d` → `docker logs kb-api 2>&1 | grep -i flyway`。
   
   **预期日志关键行**：Flyway 段出现 baseline 登记（version 0）+ `Migrating schema ... to version "1 - baseline schema"`（或 skip）字样，应用正常启动完成。
4. **校验演练库 history**：
   ```bash
   psql -h 127.0.0.1 -U <db_user> -d kb_rag_agent_flyway_drill \
     -c "SELECT installed_rank, version, description, success FROM flyway_schema_history ORDER BY installed_rank;"
   ```
   **预期两行**：version=0（BASELINE）与 version=1（baseline_schema），success 均 `t`。再 `\dt` 确认 10 张业务表结构与演练前一致（V1 全 IF NOT EXISTS，零变更）。
5. **体现网**：演练通过后正常启动 kb-api（指向现网库 `kb_rag_agent`，即现有启动方式），首跑自动完成同样的 baseline 登记；用第 4 步同一条 SQL 对现网库校验两行。
6. **清理（可选）**：`dropdb -h 127.0.0.1 -U <db_user> kb_rag_agent_flyway_drill`（备份 dump 建议保留至批3 灾备演练衔接）。

**预期回传**：现网库 flyway_schema_history 两行文本 + 启动日志 Flyway 段关键行。

**回滚**：`psql -d kb_rag_agent -c "DROP TABLE flyway_schema_history;"` 即回接入前状态；或 env `FLYWAY_ENABLED=false` 整体关闭（业务表零影响）。

## F3 · kb-api 容器化部署（簇⑥ 批1b，v2.55）

**目的**：生产 ECS 从 fat jar 直起切换为容器化形态（4.11 验收组成：healthcheck/自动重启/镜像版本化/日志轮转 + AppCDS）。

**前置**：
- ECS 已安装 docker + docker compose v2（`docker compose version` 确认 v2）；
- 代码同步至 ECS（部署目录按 `/opt/kb-rag-agent`）；
- 存量服务运行中：PG 宿主原生 + ES/Redis/MinIO/Milvus 既有 compose；
- 本机可跑 Maven 构建（ECS 2 核不做镜像内构建，宿主侧出 jar 再 docker build）。

**步骤**：

1. **构建镜像**：
   ```bash
   cd /opt/kb-rag-agent
   bash infra/scripts/build-image.sh
   ```
   输出末行 `KB_IMAGE_TAG=v1.0.0-<git短哈希>`——**记下这个 tag**。
2. **配置 Secrets**：
   ```bash
   cd /opt/kb-rag-agent/infra
   cp .env.example .env && chmod 600 .env
   vi .env   # 或用你习惯的编辑器
   ```
   逐项填写：所有 `CHANGE_ME` 改实值；`KB_IMAGE_TAG` 填第 1 步输出。主机名约定 `host.docker.internal`（PG 原生 :5432 与存量 compose 宿主映射端口统一经此）——存量服务若宿主端口与模板缺省不符（5432/9200/6379/9000/19530），按实改端口号。
3. **首次启动**：
   ```bash
   cd /opt/kb-rag-agent/infra
   docker compose -f docker-compose.app.yml up -d
   docker compose -f docker-compose.app.yml ps        # 等 kb-api 转 healthy（start_period 90s）
   curl -s localhost:8090/actuator/health             # 预期 {"status":"UP"}
   ```
   ⚠️ 首跑 Flyway 自动 baseline 登记（与 F1 同一机制；F1 未先行则此处即现网首跑——V1 幂等零变更）。异常时 `docker logs kb-api | tail -50` 定位。
4. **AppCDS 训练（可选但建议）**：
   ```bash
   cd /opt/kb-rag-agent/infra
   docker compose -f docker-compose.app.yml --profile tools run --rm kb-api-cds-train
   ```
   观察输出 `[cds-train] archive written OK` 与 `/opt/cds/app.jsa` 大小（训练 = 完整启动一次，需 infra 可达，约 1-2 分钟；超时时长 `CDS_TRAIN_TIMEOUT` 缺省 150s 可调）。然后：
   ```bash
   docker compose -f docker-compose.app.yml restart kb-api
   docker logs kb-api 2>&1 | grep -i "\[entrypoint\]"   # 预期见 AppCDS archive detected
   ```
   **实测两项回传**：① `--enable-preview` 与 CDS 兼容性——训练失败（日志 WARN archive absent）则保持无 CDS 运行并登记降级，零功能影响；② 有/无 archive 启动耗时对比（`docker logs` 中启动完成时间戳差值）。
5. **自愈验证**：`docker kill kb-api` → `docker compose -f docker-compose.app.yml ps` 观察 30s 内自动拉起回 healthy。
6. **开机自启**：
   ```bash
   cp /opt/kb-rag-agent/infra/kb-api.service /etc/systemd/system/
   # 代码目录非 /opt/kb-rag-agent 时先改 unit 内 WorkingDirectory
   systemctl daemon-reload && systemctl enable --now kb-api
   reboot   # 重启后 docker ps 确认 kb-api healthy + curl health UP
   ```

**预期回传**：compose ps healthy 输出 + health UP + CDS 训练结果（成/败 + 启动耗时对比）+ kill 自愈与 reboot 自启结果。

**回滚**：`docker compose -f docker-compose.app.yml down` 后回到 fat jar 直起形态（产物与配置独立，零破坏）。

- ⚠️ 步骤 6 的 d/e 两项会临时改 `.env` 凭据并重启 kb-api——演练窗口内服务降级，按步骤恢复即可。

**步骤**：

1. **同步代码**：将仓库最新代码同步至 ECS `/opt/kb-rag-agent`（git pull 或既有同步通道）；
2. **启动监控栈**：
   ```bash
   cd /opt/kb-rag-agent/infra
   docker compose -f docker-compose.monitoring.yml up -d
   docker compose -f docker-compose.monitoring.yml ps
   ```
   预期：prometheus / grafana 状态 healthy（start_period 30s 内转绿），node-exporter / jaeger running（jaeger scratch 基座无 healthcheck，实证留档，running 即正确）；
3. **采集目标验证**：浏览器开 `http://<ECS_IP>:9090/targets`（或 `curl -s localhost:9090/api/v1/targets`），预期 **kb-rag-agent 与 node-exporter 两个 job 均 UP**。kb-rag-agent 若 DOWN：先 `curl localhost:8090/actuator/health` 确认 kb-api healthy（回 F3 排查），再看 prometheus 日志 `docker compose -f docker-compose.monitoring.yml logs prometheus | tail -20`；
4. **Grafana 面板验证**：浏览器开 `http://<ECS_IP>:3000`，用 GRAFANA_ADMIN_USER/PASSWORD 登录 → 左侧 Dashboards → KB-RAG 文件夹四面板（概览/检索/LLM/业务）。先造流量（前端对话几轮或下面第 6 步的循环命令），面板应见曲线；数据源 uid=prometheus 已 provisioning 钉死，无需手配；
5. **合成单测（7 条）**：
   ```bash
   cd /opt/kb-rag-agent/infra
   docker compose -f docker-compose.monitoring.yml exec prometheus \
     promtool check rules /etc/prometheus/rules/alert-rules-kb-rag.yml
   docker compose -f docker-compose.monitoring.yml exec prometheus \
     promtool test rules /etc/prometheus/rules-selfcheck/alert-rules-selfcheck-test.yml
   ```
   预期：`SUCCESS` + 7 用例全 PASS。**若有 FAIL**：回传 expected/actual 差异即可（期望值为无 promtool 环境下的算法推导，以实测为准，机器侧修订单测文件并回写）；
6. **真触发演练（6 条，逐条做，每条完成后恢复现场；观察点 = 浏览器 `:9090/alerts` 页 FIRING 态）**。通用请求循环命令（同步端点，JWT 按实替换，query 按各条要求换）：
   ```bash
   JWT='<Casdoor 令牌>'
   for i in $(seq 1 25); do
     curl -s -X POST http://localhost:8090/api/v1/chat \
       -H "Authorization: Bearer $JWT" -H 'Content-Type: application/json' \
       -d '{"query":"自检查询'"$i"'","sessionId":"selfcheck-m1","mode":"rag"}' \
       -o /dev/null -w "%{http_code}\n"
   done
   ```
   a) **KbProcessRecentlyRestarted**：`docker restart kb-api` → 等约 1.5 分钟（for 1m + 评估间隔）→ alerts 页 FIRING；uptime 满 5 分钟后自动恢复。零配置改动。
   b) **KbQuotaHitRateHigh**：`infra/.env` 增改 `RAG_RATELIMIT_RATE=2`（窗口 60s 不变）→ `docker compose -f docker-compose.app.yml up -d`（重建 kb-api 生效）→ 跑循环命令 25 次（多数返回 429 正常）→ 命中率 >3% 持续 10 分钟 FIRING → 恢复 `RAG_RATELIMIT_RATE=60`（或删除该行）再 up -d；
   c) **KbRejectionRateHigh**：从运维中心第五 Tab（护栏词表）任选一条**注入侧 BLOCK 档**词项（红线纪律：本清单不写字面载荷，以系统内既有 BLOCK 词项原值构造）→ 循环命令 query 均含该词项，跑 25 次 → 拒绝率 >15% 持续 10 分钟 FIRING；
   d) **KbRequestErrorRateHigh**（⚠️ 主模型全失效模拟，演练窗口尽量短）：`.env` 改 `DEEPSEEK_API_KEY=invalid-drill` + `RAG_ROUTING_FALLBACK_ENABLED=false` → up -d 重建 → 循环 12 次（返回 ERROR 正常）→ 错误率 >5% 持续 5 分钟 FIRING → **立即**恢复两项原值 up -d；
   e) **KbRerankFallbackRateHigh**：`.env` 改 `RERANK_ENDPOINT=http://127.0.0.1:9`（不可达即降级）→ up -d → 循环 25 次 → 降级率 >10% 持续 10 分钟 FIRING → 恢复原值 up -d；
   f) **KbEmptyRetrievalRateHigh**（窗口最长，建议最先发起与其他项并行孵化）：用**空语料租户**（无文档的测试租户 JWT，或临时新建）循环 25 次 → 空检索率 >10% 持续 15 分钟 FIRING；
   （各条 `for` 持续时间见上，b/c/e 约 10-15 分钟/条，全程含恢复约 1.5 小时；`docker compose -f docker-compose.app.yml ps` 确认每次重建后 kb-api 回 healthy 再继续下一条。）
7. **开机自启（建议）**：
   ```bash
   cp /opt/kb-rag-agent/infra/kb-monitoring.service /etc/systemd/system/
   # 如代码目录非 /opt/kb-rag-agent，先改 unit 内 WorkingDirectory
   systemctl daemon-reload && systemctl enable --now kb-monitoring
   ```

- ECS 宿主已安装 mc（MinIO Client）：
  ```bash
  curl -fsSL https://dl.min.io/client/mc/release/linux-amd64/mc -o /usr/local/bin/mc \
    && chmod +x /usr/local/bin/mc && mc --version
  ```
- `infra/.env` 备份段已按 `.env.example` 补齐（`BACKUP_PG_HOST/PORT/DATABASE` 按宿主侧地址，缺省 127.0.0.1:5432/kb_rag_agent 即可；DB 与 MinIO 凭据复用既有键，无需重复填）。

**步骤**：

1. **手工备份首跑**：
   ```bash
   cd /opt/kb-rag-agent
   bash infra/scripts/pg-backup.sh
   ```
   预期末两行：`UPLOAD OK（--md5 校验通过 + 远端 stat 存在）` 与 `SUCCESS: 备份完成（本地 + MinIO 双副本）`。核验双副本：
   ```bash

   ```
2. **恢复演练（严格口径）**：⚠️ 演练在独立库 `kb_rag_agent_drill` 进行，不触生产库；严格口径要求**备份后到演练间无写入**（择业务空窗，或接受 LAG 判定去掉 `--strict`）：
   ```bash
   bash infra/scripts/pg-restore-drill.sh --strict
   ```
   预期：逐表 `MATCH` + `RESULT: PASS`。
   - 若报 vector 扩展权限错（备份含 `CREATE EXTENSION IF NOT EXISTS vector`，非超级用户无法新装）——以 postgres 超级用户对演练库补装后重跑：
     ```bash
     sudo -u postgres psql -d kb_rag_agent_drill -c 'CREATE EXTENSION IF NOT EXISTS vector;'
     ```

**目的**：运行时口径复核攻击语料四分区覆盖（基线锚点 BLOCK/KEYWORD/TRIGGER/SILENT = 47/13/9/58），静默区扩词经带外通道。**词表变更后分区会移动——请在词表形态稳定时执行**。

   ```bash

   ```
   该测试强制干净集 110 条 BLOCK+FLAG 全档零命中（绿 = 守住；红 = 新词有误伤，先处理再转 BLOCK）。

4. **扩词后回归**：重复第 1、2 步确认静默区收敛且干净集零命中不破；DB 单轨下写操作自动触发热重载，无需手动发信号。

**预期回传**：四分区计数 + 干净集零命中复算结果（绿/红）；如有扩词，附新增词项 ID 段与档位（FLAG/BLOCK）。
