# 领域驱动设计（DDD）全面深度解析

---

## 一、DDD 概述

### 1.1 起源与背景

**领域驱动设计（Domain-Driven Design，简称 DDD）** 由 **Eric Evans** 于 2003 年在其著作《Domain-Driven Design: Tackling Complexity in the Heart of Software》（中文译名：《领域驱动设计：软件核心复杂性应对之道》，俗称"蓝皮书"）中首次系统性提出。此后，Vaughn Vernon 的《Implementing Domain-Driven Design》（"红皮书"）和《Domain-Driven Design Distilled》（"绿皮书"）进一步完善和推广了该方法论。

DDD 的诞生背景是：传统软件开发中，业务需求往往被技术实现淹没，导致 **"贫血模型"** 盛行——领域对象只包含数据（getter/setter），所有业务逻辑堆积在服务层（Service Layer），代码与业务严重脱节，系统难以维护和演进。

### 1.2 核心思想

DDD 的核心思想可以概括为以下几点：

| 核心原则 | 说明 |
|---------|------|
| **以领域为核心** | 将软件的核心复杂性聚焦于业务领域本身，技术为业务服务 |
| **模型驱动设计** | 通过建立精确的领域模型来驱动软件设计，让软件成为业务领域的映射 |
| **通用语言** | 开发人员与领域专家使用统一的语言进行沟通，确保业务概念在代码、设计及沟通中的一致性 |
| **限界上下文** | 明确划定模型的适用边界，避免大泥球式的混乱 |
| **战略+战术** | 宏观上划分边界（战略设计），微观上精细建模（战术设计） |

### 1.3 适用场景

DDD **不是银弹（能解决所有问题的万能方法）**，它主要适用于：
- **业务逻辑复杂**的系统（如金融交易、保险理赔、电商交易、供应链管理等）
- 需要长期演进和维护的**企业级核心系统**
- 团队规模较大，需要**清晰的边界划分**以支持并行开发

**不适用于**：
- 简单的 CRUD 应用
- 以技术复杂度为主（如高性能计算、编译器）的系统
- 团队过小、项目周期极短的初创项目

## 二、通用语言（Ubiquitous Language）

### 2.1 定义

通用语言是**围绕领域模型建立的一套统一术语和表达方式**，由领域专家和开发人员共同定义和维护。它贯穿于需求文档、设计文档、代码命名、数据库字段、测试用例等所有环节。

### 2.2 作用与价值

- **消除歧义**：同一个业务概念在所有人心中有唯一、明确的含义
- **知识沉淀**：业务知识不再是"只存在于某人脑中"的隐性知识
- **代码即文档**：代码中的类名、方法名直接反映业务术语，降低理解成本

### 2.3 实践要点

- 使用**领域专家的原生词汇**（如"理赔"而非"处理退款请求"）
- 同一术语在不同限界上下文中可以有**不同含义**（如"商品"在销售域和仓储域含义不同）
- 建立**术语表（Glossary）**，持续维护和更新
- 如果开发人员在代码中使用了领域专家听不懂的技术术语，说明通用语言出了问题

## 三、战略设计（Strategic Design）——宏观架构

战略设计关注的是**如何在宏观层面划分和管理复杂业务系统**，解决"系统拆成几块、块与块之间如何协作"的问题。

### 3.1 领域与子域（Domain & Subdomain）

**领域（Domain）** 是软件所要解决的业务问题空间。一个复杂的业务领域通常需要拆分为多个**子域（Subdomain）**。

#### 子域的三种类型：

| 子域类型 | 说明 | 投入策略 | 举例 |
|---------|------|---------|------|
| **核心域（Core Domain）** | 企业的核心竞争力所在，是业务差异化的关键 | **重点投入**，最优秀的人才，精细建模 | 电商的推荐算法、物流的路径规划 |
| **支撑子域（Supporting Subdomain）** | 为核心域提供支持，有一定业务特殊性，但非核心 | **适度投入**，可自建也可外包 | 电商的客户服务系统、发票系统 |
| **通用子域（Generic Subdomain）** | 通用能力，没有业务特殊性，市面上有成熟方案 | **尽量采购/使用开源**，避免重复造轮子 | 身份认证、消息通知、日志系统 |

> **战略洞察**：识别核心域是 DDD 战略设计的第一步。资源有限时，必须将最好的工程力量投入到核心域。

### 3.2 限界上下文（Bounded Context）

**限界上下文是 DDD 中最重要的战略设计概念。**

#### 3.2.1 定义

限界上下文是一个**显式定义的语义边界和业务边界**。在这个边界内：
- 领域模型中的每一个术语都有**唯一且明确的含义**
- 业务规则是**自洽和一致的**
- 模型不需要与边界外的模型保持一致

#### 3.2.2 为什么需要限界上下文？

在大型系统中，试图建立一个全局统一的领域模型是不现实的，原因如下：
- **语义冲突**：同一个词在不同业务场景中含义不同。例如：
  - "用户"在**账户上下文**中是登录凭证（用户名、密码）
  - "用户"在**订单上下文**中是收货人（姓名、地址、电话）
  - "用户"在**风控上下文**中是信用主体（信用评分、历史记录）
- **认知负荷**：一个巨大的全局模型超出了任何人的理解能力
- **团队协作**：不同团队负责不同业务，需要独立的模型空间

#### 3.2.3 限界上下文的三重边界

| 边界类型 | 说明 |
|---------|------|
| **语义边界** | 同一术语在边界内有唯一含义，跨边界需要翻译 |
| **模型边界** | 领域模型只在边界内有效，不跨越边界引用 |
| **团队/物理边界** | 通常一个限界上下文由一个团队负责，可独立部署（微服务） |

#### 3.2.4 限界上下文与子域的关系

- **理想状态**：一个子域对应一个限界上下文（1:1）
- **现实情况**：一个子域可能被拆分为多个限界上下文，或者一个限界上下文包含多个子域（遗留系统常见）

#### 3.2.5 识别限界上下文的方法

- **事件风暴（Event Storming）**：通过识别领域事件，聚合命令和聚合，自然浮现出边界
- **语言边界**：当同一个术语需要加前缀才能区分时，说明可能跨越了上下文
- **业务能力分析**：根据组织的业务能力矩阵进行划分

### 3.3 上下文映射（Context Mapping）

限界上下文不是孤岛，它们之间必须协作完成完整的业务流程。**上下文映射**定义了不同限界上下文之间的**集成关系和团队协作模式**。

Eric Evans 定义了 **9 种上下文映射模式**：

---

#### ① 合作关系（Partnership）

- **定义**：两个上下文的团队以合作的方式协同工作，共同规划演进路线，互相配合接口变更
- **适用场景**：两个团队属于同一组织，目标一致，且高度依赖
- **风险**：协调成本高，一方延期会影响另一方

#### ② 共享内核（Shared Kernel）

- **定义**：两个上下文共享一小部分领域模型（通常是一个共享的代码库/包），对共享部分的修改需要双方协商
- **适用场景**：两个上下文有少量重叠的核心概念
- **风险**：共享内核容易膨胀，最终变成紧耦合
- **最佳实践**：共享内核应尽量小，定期审查，避免滥用

#### ③ 客户-供应商（Customer-Supplier）

- **定义**：上游（供应商）为下游（客户）提供服务，上游团队在规划时会优先考虑下游的需求
- **适用场景**：上下游团队属于同一组织，且上游愿意响应下游需求
- **机制**：通常有正式的需求沟通渠道和迭代计划

#### ④ 遵奉者（Conformist）

- **定义**：下游团队没有谈判能力，必须**完全遵奉**上游团队的模型和接口，无法要求上游做出改变
- **适用场景**：上游是外部第三方系统（如微信支付 API），或者上游是组织内的强势团队
- **策略**：下游要么全盘接受上游模型，要么引入防腐层进行隔离

#### ⑤ 防腐层（Anti-Corruption Layer, ACL）⭐

**防腐层是 DDD 中最具实战价值的模式之一。**

- **定义**：在下游限界上下文中创建一个**隔离层**，将上游（外部系统）的模型翻译成下游自己的领域模型，防止外部模型"污染"下游的领域模型
- **核心目的**：保护下游领域模型的**纯净性和独立性**

**防腐层的组成**：

```
┌───────────────────────────────────────────────────┐
│              下游限界上下文                       │
│                                                   │
│  ┌──────────────┐    ┌──────────────┐             │
│  │  领域模型    │◄── │  防腐层(ACL) │◄── 外部API  │
│  │  (纯净)      │    │  适配器      │             │
│  └──────────────┘    │  转换器      │             │
│                      │  外观(Facade)│             │
│                      └──────────────┘             │
└───────────────────────────────────────────────────┘
```

**防腐层内部的三个角色**：
- **Facade（外观）**：简化对外部系统的调用接口，隐藏外部系统的复杂性
- **Adapter（适配器）**：将外部系统的调用方式适配为本地习惯的方式
- **Translator（转换器）**：将外部系统的数据模型翻译为本地领域模型

**典型应用场景**：
- 集成遗留系统（老系统的数据模型混乱，不能直接引入新系统）
- 对接第三方服务（支付网关、物流追踪等外部 API）
- 微服务间集成（上游服务的模型变更不应影响下游）

**代码示例（伪代码）**：

```java
// 防腐层中的适配器
public class ExternalPaymentAdapter {
    
    private final ExternalPaymentGateway gateway; // 外部支付网关
    
    // 将外部模型翻译为本地领域模型
    public PaymentResult processPayment(PaymentCommand command) {
        // 1. 将本地命令转换为外部请求格式
        ExternalPayRequest extRequest = translateToExternal(command);
        
        // 2. 调用外部系统
        ExternalPayResponse extResponse = gateway.pay(extRequest);
        
        // 3. 将外部响应翻译为本地领域模型
        return translateToLocal(extResponse);
    }
}
```

#### ⑥ 开放主机服务（Open Host Service, OHS）⭐

- **定义**：上游限界上下文为**所有下游**提供一套**标准化的公共 API 接口**，而非为每个下游定制接口
- **核心目的**：降低集成复杂度，提供一致的服务体验
- **与 ACL 的关系**：OHS 是上游的"供给侧"策略，ACL 是下游的"消费侧"策略，两者经常配合使用

**实践要点**：
- API 需要有完善的文档（如 OpenAPI/Swagger）
- 接口版本管理（如 v1, v2）
- 向后兼容承诺

#### ⑦ 发布语言（Published Language, PL）

- **定义**：为跨上下文的通信定义一种**标准化的数据交换格式**（通常是 XML Schema、JSON Schema、Protocol Buffers 等）
- **核心目的**：消除不同上下文之间的数据格式歧义
- **常与 OHS 配合使用**：OHS 定义接口协议，PL 定义数据格式

**常见实现**：
- REST API + JSON Schema
- gRPC + Protocol Buffers
- 消息队列 + Avro/Thrift

#### ⑧ 各行其道（Separate Ways）

- **定义**：两个上下文之间**没有集成关系**，各自独立演进
- **适用场景**：两个子域之间确实没有业务交互，或者集成的成本远大于独立维护的成本
- **注意**：需要警惕"虚假的各行其道"——实际上有数据冗余和一致性隐患

#### ⑨ 大泥球（Big Ball of Mud）

- **定义**：系统中存在**质量低劣、边界混乱**的遗留部分，没有清晰的模型和边界
- **策略**：不要试图去改造它，而是用**防腐层**将其隔离，保护新系统不受污染
- **态度**：承认现实，划定边界，逐步绞杀（配合绞杀者模式）

## 四、战术设计（Tactical Design）——微观建模

战术设计关注的是**在单个限界上下文内部**，如何精细地构建领域模型，并将其落地为代码。

### 4.1 实体（Entity）

- **定义**：具有**唯一标识（Identity）**的对象，通过标识来区分，而不是通过属性值
- **核心特征**：
  - 有唯一标识（如 ID、UUID）
  - 具有**生命周期**（创建、修改、销毁）
  - 可变（Mutable），状态会随时间变化
  - 两个实体即使属性完全相同，只要标识不同就是不同的实体

```java
public class Order {
    private OrderId id;          // 唯一标识
    private OrderStatus status;  // 状态
    private Money totalAmount;   // 金额
    
    // 实体可以修改自身状态，但必须通过业务方法
    public void confirm() {
        if (this.status != OrderStatus.PENDING) {
            throw new IllegalStateException("只有待确认的订单才能确认");
        }
        this.status = OrderStatus.CONFIRMED;
        // 发布领域事件
        registerEvent(new OrderConfirmedEvent(this.id));
    }
}
```

### 4.2 值对象（Value Object）

- **定义**：没有唯一标识，通过**属性值**来判等的对象
- **核心特征**：
  - **无唯一标识**
  - **不可变（Immutable）**：一旦创建就不能修改，需要变更时创建新实例
  - 通过属性值判等（equals 基于所有属性）
  - 可以包含业务逻辑（充血模型）
  - 可以被自由替换和共享

```java
public final class Money {
    private final BigDecimal amount;
    private final Currency currency;
    
    public Money(BigDecimal amount, Currency currency) {
        this.amount = amount;
        this.currency = currency;
    }
    
    public Money add(Money other) {
        if (!this.currency.equals(other.currency)) {
            throw new IllegalArgumentException("币种不同不能相加");
        }
        return new Money(this.amount.add(other.amount), this.currency);
    }
    
    // equals 基于值
    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Money money)) return false;
        return amount.compareTo(money.amount) == 0 
            && currency.equals(money.currency);
    }
}
```

**实体 vs 值对象的判断标准**：
| 维度 | 实体 | 值对象 |
|------|------|--------|
| 标识 | 有唯一标识 | 无标识，靠值判等 |
| 可变性 | 可变 | 不可变 |
| 生命周期 | 有独立生命周期 | 依附于实体 |
| 举例 | 订单、用户、商品 | 金额、地址、日期范围 |

### 4.3 聚合与聚合根（Aggregate & Aggregate Root）⭐

**聚合是 DDD 战术设计中最核心、也最难掌握的概念。**

#### 4.3.1 定义

- **聚合（Aggregate）**：一组**紧密关联的领域对象**的集合，作为**数据修改和事务一致性**的单元
- **聚合根（Aggregate Root）**：聚合的**入口对象**，外部只能通过聚合根来访问和修改聚合内部的对象

#### 4.3.2 核心规则

| 规则 | 说明 |
|------|------|
| **外部只引用聚合根** | 其他聚合只能通过聚合根的 ID 来引用，不能直接持有聚合内部对象的引用 |
| **聚合内部保持一致性** | 聚合根负责保证聚合内所有业务规则的不变量（Invariant）在事务结束时成立 |
| **跨聚合使用最终一致性** | 不同聚合之间不保证强一致性，通过领域事件实现最终一致性 |
| **聚合要尽量小** | 只包含真正需要在同一事务中修改的对象，避免大聚合导致的并发冲突 |

#### 4.3.3 设计原则

```
┌───────────────────────────────────────────────────────┐
│        订单聚合（Order Aggregate）                    │
│                                                       │
│   ┌──────────┐                                        │
│   │  Order   │──── 包含 ────► OrderItem               │
│   │(聚合根)  │                                        │
│   │          │──── 包含 ────► ShippingAddress (值对象)│
│   └──────────┘                                        │
│                                                       │
│   ⚠ 外部不能直接修改 OrderItem                       │
│   必须通过 Order.add/removeItem()                     │
└───────────────────────────────────────────────────────┘
         │
         │ 通过ID引用（不直接持有对象）
         ▼
┌──────────────────┐
│ 商品聚合         │
│ Product(聚合根)  │
└──────────────────┘
```

**聚合设计的黄金法则**：
1. **在一致性边界内设计聚合**：只有真正需要在同一事务中保持一致性的对象才放在同一个聚合
2. **设计小聚合**：大聚合会导致锁竞争激烈、并发性能差
3. **通过 ID 引用其他聚合**：而非对象引用
4. **使用最终一致性更新其他聚合**：通过领域事件异步更新

### 4.4 领域服务（Domain Service）

- **定义**：当某个业务操作**不属于任何实体或值对象**时，将其放入领域服务
- **核心特征**：
  - **无状态（Stateless）**
  - 操作涉及**多个聚合**的协调
  - 属于**领域层**，不是应用层
  - 名称应体现业务含义

```java
// 领域服务示例：转账操作涉及两个账户聚合
public class TransferService {
    
    public void transfer(Account fromAccount, Account toAccount, Money amount) {
        // 业务规则：不能跨币种转账
        if (!fromAccount.getCurrency().equals(toAccount.getCurrency())) {
            throw new CrossCurrencyTransferException();
        }
        fromAccount.debit(amount);   // 扣款
        toAccount.credit(amount);    // 入账
    }
}
```

**区分领域服务与应用服务**：

| 维度 | 领域服务 | 应用服务 |
|------|---------|---------|
| 位置 | 领域层 | 应用层 |
| 职责 | 核心业务逻辑 | 编排用例、协调基础设施 |
| 包含业务规则 | ✅ 是 | ❌ 否（仅做编排） |
| 示例 | TransferService（转账逻辑） | OrderAppService（编排创建订单流程） |

### 4.5 领域事件（Domain Event）⭐

- **定义**：表示领域中发生的**重要业务事件**，是过去发生的事实
- **命名规范**：使用**过去时态**（如 `OrderCreated`、`PaymentCompleted`）
- **核心特征**：
  - **不可变**：事件一旦发生就不能修改
  - 包含事件发生的**时间戳**和**相关数据**
  - 用于**解耦聚合**和**实现最终一致性**

```java
public class OrderCreatedEvent implements DomainEvent {
    private final OrderId orderId;
    private final CustomerId customerId;
    private final Money totalAmount;
    private final LocalDateTime occurredOn;
    
    // 事件是不可变的
    // ...
}

// 在聚合根中发布事件
public class Order {
    public void create(List<OrderItem> items) {
        // 业务逻辑...
        this.status = OrderStatus.CREATED;
        
        // 注册领域事件
        this.registerEvent(new OrderCreatedEvent(
            this.id, this.customerId, this.totalAmount, LocalDateTime.now()
        ));
    }
}
```

**领域事件的作用**：
1. **聚合间解耦**：订单创建后发布事件，库存服务、通知服务各自监听处理
2. **最终一致性**：跨聚合的数据一致性通过事件异步实现
3. **审计与溯源**：事件流本身就是完整的业务日志
4. **CQRS 和事件溯源的基础**

### 4.6 工厂（Factory）

- **定义**：封装**复杂对象创建逻辑**的设计模式
- **适用场景**：
  - 聚合的创建涉及复杂的业务规则和多个对象的组装
  - 需要根据条件创建不同的具体实现
- **分类**：
  - **工厂方法**：在聚合根上提供创建方法
  - **独立工厂类**：当创建逻辑过于复杂时使用

```java
public class OrderFactory {
    public static Order createOrder(CustomerId customerId, List<ProductInfo> products) {
        // 1. 校验业务规则
        // 2. 计算价格
        // 3. 组装聚合
        Order order = new Order(OrderId.generate(), customerId);
        products.forEach(p -> order.addItem(p));
        return order;
    }
}
```

### 4.7 仓储（Repository）

- **定义**：为聚合提供**持久化抽象**，模拟一个内存中的集合
- **核心原则**：
  - **每个聚合根对应一个仓储**，不为聚合内部对象单独建仓储
  - 仓储接口定义在**领域层**，实现在**基础设施层**（依赖倒置）
  - 对调用方隐藏底层存储细节（数据库、文件系统等）

```java
// 领域层定义接口
public interface OrderRepository {
    Order findById(OrderId id);
    void save(Order order);
    void remove(Order order);
    List<Order> findByCustomer(CustomerId customerId);
}

// 基础设施层实现
public class JpaOrderRepository implements OrderRepository {
    private final OrderJpaRepository jpaRepository;
    
    @Override
    public void save(Order order) {
        // ORM 映射、持久化...
    }
}
```

### 4.8 规约（Specification）

- **定义**：将**业务规则封装为可复用的、可组合的对象**
- **核心特征**：
  - 本质是一个**谓词（Predicate）**，判断某个对象是否满足条件
  - 可以组合（AND、OR、NOT）
  - 可用于验证、查询过滤、对象创建等多种场景

```java
public interface Specification<T> {
    boolean isSatisfiedBy(T candidate);
    
    default Specification<T> and(Specification<T> other) {
        return candidate -> this.isSatisfiedBy(candidate) 
                         && other.isSatisfiedBy(candidate);
    }
}

// 示例：订单金额超过1000元的规约
public class HighValueOrderSpec implements Specification<Order> {
    @Override
    public boolean isSatisfiedBy(Order order) {
        return order.getTotalAmount().isGreaterThan(Money.of(1000));
    }
}
```

## 五、DDD 架构模式

DDD 需要合适的架构来支撑领域模型的独立性。以下是几种主流架构模式：

### 5.1 四层架构（Layered Architecture）

Eric Evans 在蓝皮书中提出的经典分层：

```
┌───────────────────────────────┐
│    展现层 (UI/Presentation)   │  ← 用户界面、API 端点
├───────────────────────────────┤
│    应用层 (Application)       │  ← 用例编排、事务管理、安全
├───────────────────────────────┤
│    领域层 (Domain)            │  ← 核心业务逻辑、领域模型 ★
├───────────────────────────────┤
│    基础设施层 (Infrastructure)│  ← 数据库、消息队列、外部服务
└───────────────────────────────┘
```

**依赖规则**：上层依赖下层，领域层不依赖任何其他层（通过依赖倒置实现）。

### 5.2 六边形架构 / 端口与适配器（Hexagonal Architecture）

由 Alistair Cockburn 提出，核心思想是**领域层处于中心，通过端口（Port）与外界交互，适配器（Adapter）实现端口**：

```
              ┌─── REST Controller (入站适配器)
              │
   ┌──────────┤
   │  端口    ├─── Message Listener (入站适配器)
   │ (Port)   │
   │          ├─── REST API (出站适配器) ─── 外部服务
   │  领域    │
   │  核心    ├─── Repository (出站适配器) ─── 数据库
   │          │
   └──────────┤
              ├─── Event Publisher (出站适配器) ─── 消息队列
              │
```

- **入站端口（Driving Port）**：定义外部如何调用领域（如接口）
- **入站适配器（Driving Adapter）**：实现入站端口（如 REST Controller、消息监听器）
- **出站端口（Driven Port）**：定义领域如何调用外部（如 Repository 接口）
- **出站适配器（Driven Adapter）**：实现出站端口（如 JPA Repository 实现、HTTP 客户端）

### 5.3 洋葱架构（Onion Architecture）

由 Jeffrey Palermo 提出，强调**领域模型是核心，依赖方向从外向内**：

```
     ┌─────────────────────────────┐
     │   Infrastructure (最外层)   │
     │  ┌───────────────────────┐  │
     │  │   Application         │  │
     │  │  ┌─────────────────┐  │  │
     │  │  │   Domain        │  │  │
     │  │  │  (核心，无依赖) │  │  │
     │  │  └─────────────────┘  │  │
     │  └───────────────────────┘  │
     └─────────────────────────────┘
```

### 5.4 整洁架构（Clean Architecture）

由 Robert C. Martin（Uncle Bob）提出，与六边形架构和洋葱架构理念一致：

```
Entities → Use Cases → Interface Adapters → Frameworks & Drivers
 (领域)    (应用层)      (适配器层)            (框架/工具层)
```

> **小结**：以上四种架构的本质思想相同——**领域层是核心，不依赖任何外部事物；外部通过抽象（接口）与领域交互；依赖方向始终指向内部**。

## 六、CQRS（命令查询职责分离）

### 6.1 定义

**CQRS（Command Query Responsibility Segregation）** 由 Greg Young 提出，核心思想是将系统的**写操作（Command）**和**读操作（Query）**从模型层面进行分离：

```
                    ┌─────────────────┐
    Command ──────► │   写模型        │ ────► 写数据库
    (创建/修改)     │   (领域模型)    │
                    └────────┬────────┘
                             │ 领域事件
                             ▼
                    ┌─────────────────┐
    Query ────────► │   读模型        │ ◄──── 读数据库
    (查询)          │   (DTO/视图模型)│      (投影/物化视图)
                    └─────────────────┘
```

### 6.2 Command 侧（写侧）

- 使用**领域模型**（聚合根、实体、值对象）处理业务逻辑
- 保证数据一致性和业务规则
- 操作粒度为**聚合**

### 6.3 Query 侧（读侧）

- 绕过领域模型，**直接查询数据库**返回 DTO
- 可以使用**非规范化的读模型**（物化视图、搜索引擎等）
- 性能优化不受领域模型约束

### 6.4 适用场景

- 读写比例严重不对称的系统（读远大于写）
- 读写模型差异大的系统（如复杂的报表查询）
- 需要独立优化读写性能的系统

### 6.5 注意事项

- CQRS 增加了系统复杂度，**不要在没有必要的场景使用**
- CQRS **不要求**物理分离数据库（可以同库不同表/视图），但物理分离效果更好
- CQRS 常与**事件溯源**配合使用

## 七、事件溯源（Event Sourcing）

### 7.1 定义

传统持久化方式存储的是**实体的当前状态**（如数据库中一条记录）。**事件溯源**存储的是**导致状态变化的一系列事件**，通过重放事件来重建实体状态。

```
传统方式：UPDATE account SET balance = 150 WHERE id = 1

事件溯源：
  Event 1: AccountCreated(id=1, initialBalance=100)
  Event 2: MoneyDeposited(id=1, amount=100)
  Event 3: MoneyWithdrawn(id=1, amount=50)
  
  当前余额 = 100 + 100 - 50 = 150
```

### 7.2 核心优势

| 优势 | 说明 |
|------|------|
| **完整审计轨迹** | 每一次变更都有记录，满足合规需求 |
| **时间旅行** | 可以重建任意时间点的状态 |
| **灵活的读模型** | 新需求出现时，可以从事件流重新投影出新的读模型 |
| **天然适配 CQRS** | 事件流是写模型和读模型之间的桥梁 |

### 7.3 挑战

- **查询复杂度**：不能直接查询当前状态，需要重放事件或使用快照（Snapshot）
- **事件版本演进**：事件结构变更时需要处理兼容性问题
- **学习曲线**：团队需要转变思维方式

### 7.4 快照（Snapshot）机制

当事件数量过多时，重放所有事件会非常耗时。解决方案是定期保存**快照**（实体在某一刻的完整状态），重放时从最近的快照开始。

## 八、系统演进模式

### 8.1 绞杀者模式（Strangler Fig Pattern）⭐

#### 8.1.1 起源

由 **Martin Fowler** 于 2004 年提出，灵感来自热带雨林中的**绞杀榕（Strangler Fig）**：这种植物的种子落在宿主树上，起初只是依附生长，随后根系逐渐延伸至地面，最终通过争夺阳光和养分将宿主树"绞杀"替代。

#### 8.1.2 核心思想

**不直接重写遗留系统，而是在其外围逐步构建新系统，通过流量路由逐渐将请求从旧系统转移到新系统，直到旧系统完全被替代。**

```
阶段1：所有请求 → [门面/网关] → 旧系统

阶段2：部分请求 → [门面/网关] → 新微服务A
       其余请求 → [门面/网关] → 旧系统

阶段3：大部分请求 → [门面/网关] → 新微服务A/B/C
       少量请求   → [门面/网关] → 旧系统(仅剩少量功能)

阶段4：所有请求 → [门面/网关] → 新微服务A/B/C
       旧系统下线 🎉
```

#### 8.1.3 实施步骤

1. **部署门面层（Facade/API Gateway）**：在旧系统前面放置一个代理层，所有请求都经过它
2. **识别迁移单元**：基于 DDD 的限界上下文，确定要迁移的业务功能
3. **构建新服务**：在新的微服务架构中实现该功能
4. **灰度切换流量**：通过路由规则（如用户ID、流量比例）逐步将请求切换到新服务
5. **验证与回滚**：对比新旧系统的结果，确认无误后扩大切换范围
6. **绞杀旧功能**：当某个功能完全切换到新服务后，关闭旧系统中对应的代码
7. **重复以上步骤**，直到旧系统完全被替代

#### 8.1.4 与 DDD 的结合

- **限界上下文**作为拆分单元：每次迁移一个限界上下文
- **防腐层**保护新系统：新系统通过 ACL 与旧系统交互，避免被旧模型污染
- **领域事件**实现协作：新旧系统可以通过事件异步协作

#### 8.1.5 适用场景

- 遗留系统体量巨大，全量重写风险过高
- 业务不能停机，需要**零中断迁移**
- 团队对旧系统理解不充分，需要渐进式探索

#### 8.1.6 风险与对策

| 风险 | 对策 |
|------|------|
| 新旧系统数据同步 | 使用双写策略或 CDC（Change Data Capture） |
| 门面层成为单点 | 高可用部署，使用成熟 API 网关 |
| 迁移周期过长 | 优先迁移高价值/高变更频率的模块 |

### 8.2 修缮者模式（Branch by Abstraction / Refactoring）

- **定义**：在**不改变外部行为**的前提下，对遗留系统的特定模块进行**隔离和内部改造**
- **适用场景**：局部架构优化，如将模块内部的混乱代码重构为 DDD 的聚合模型
- **与绞杀者的区别**：修缮者模式不替换系统，而是在原位进行改进

### 8.3 分支模式（Branching / Parallel Run）

- **定义**：新旧系统**同时运行**，对比两者的结果，确保新系统的正确性
- **机制**：
  1. 请求同时发给新旧系统
  2. 以旧系统的结果为准返回给用户
  3. 异步对比新旧结果，发现差异则报警
  4. 当差异率降到可接受水平时，切换为新系统

## 九、事件风暴（Event Storming）

### 9.1 定义

**事件风暴**是由 Alberto Brandolini 提出的一种**协作式工作坊方法**，用于快速探索复杂业务领域，是 DDD 战略设计和限界上下文识别的核心实践工具。

### 9.2 核心元素

| 元素 | 颜色 | 说明 |
|------|------|------|
| **领域事件（Domain Event）** | 🟠 橙色 | 过去发生的业务事实，如"订单已创建" |
| **命令（Command）** | 🔵 蓝色 | 触发事件的操作，如"创建订单" |
| **聚合（Aggregate）** | 🟡 黄色 | 处理命令并产生事件的业务对象 |
| **角色（Actor）** | 🟢 绿色小圆 | 发起命令的用户/系统 |
| **外部系统（External System）** | 🩷 粉色 | 不在控制范围内的第三方系统 |
| **策略（Policy）** | 🟣 紫色 | 事件触发后的自动化规则，如"当订单创建后，发送通知" |
| **读模型（Read Model）** | 🟩 浅绿 | 做出决策所需的信息 |
| **热点/问题（Hot Spot）** | 🔴 红色 | 有争议、不清楚或有风险的地方 |

### 9.3 工作坊流程

1. **无序发散**：所有参与者（领域专家+开发人员）在墙上贴出尽可能多的领域事件
2. **时间线排序**：按时间顺序排列事件，去除重复
3. **识别命令和聚合**：为每个事件找出触发它的命令和处理命令的聚合
4. **标注策略和外部系统**：完善业务流程
5. **识别限界上下文**：通过聚合和事件的自然分组，浮现出限界上下文的边界
6. **标注热点**：标记有争议或不确定的地方，留待后续深入讨论

## 十、DDD 落地实践中的常见反模式

| 反模式 | 说明 | 正确做法 |
|--------|------|---------|
| **贫血模型** | 实体只有 getter/setter，逻辑全在 Service 中 | 让实体和值对象承载业务逻辑（充血模型） |
| **上帝聚合** | 一个聚合包含了太多对象，导致性能差、并发冲突 | 拆分聚合，遵循"小聚合"原则 |
| **跨聚合直接引用** | 一个聚合直接持有另一个聚合的对象引用 | 通过 ID 引用，通过领域事件协作 |
| **仓储滥用** | 为每个实体都建仓储，或在仓储中加入复杂业务查询 | 只为聚合根建仓储，复杂查询走 CQRS 读模型 |
| **限界上下文过大** | 一个上下文包含了太多不相关的业务 | 按业务能力和语义边界细分 |
| **共享内核膨胀** | 共享内核越来越大，变成了公共泥球 | 控制共享内核大小，定期审查 |
| **DDD 教条主义** | 不顾实际情况，强制使用所有 DDD 模式 | 根据项目复杂度选择性使用 |
| **忽视通用语言** | 代码命名与业务术语脱节 | 建立和维护术语表，代码命名与业务对齐 |

## 十二、总结

领域驱动设计（DDD）不仅仅是一套技术方法论，更是一种**以业务为中心的思维方式**。它的核心价值在于：

1. **统一语言**：打破业务与技术的壁垒，让所有人"说同一种话"
2. **管理复杂性**：通过战略设计（限界上下文、子域划分）将复杂系统拆解为可管理的单元
3. **保护核心资产**：通过战术设计（聚合、充血模型）将业务知识沉淀到代码中，而非人脑中
4. **拥抱变化**：通过防腐层、上下文映射等模式隔离变化，使系统能灵活响应业务演进
5. **平滑演进**：通过绞杀者模式等策略，实现遗留系统的零中断渐进式改造

**DDD 的学习路径建议**：
1. 先读《Domain-Driven Design Distilled》（绿皮书）了解全貌
2. 再读《Implementing Domain-Driven Design》（红皮书）深入细节
3. 最后挑战《Domain-Driven Design》（蓝皮书）理解原始思想
4. 在实践中从**事件风暴**开始，逐步应用战略设计和战术设计
5. 避免教条主义，根据项目复杂度**选择性使用**DDD的模式和工具
