## 一、专项背景与定位

Phase 4 七簇推进至簇⑤收官（MCP Server 三轮 E2E 收敛全绿），原下一棒为簇⑥生产加固与压测。用户决定：**簇⑥顺延，先插入安全加固专项**，将此前「立项不排期」的护栏加固路线收尾补全。

专项动因有三：

1. **检测词表偏薄是直接动因**：注入检测默认词表仅 14 条短语干词（英文 6 + 中文 8，v2.38 补强后），输出黑名单仅 2 条占位词项；v2.38 簇⑤ MCP E2E 已实证中文同族变体可漏检（靠模型层兜底而非护栏拦截）。词表需抽成独立结构化配置并按攻击族系扩充；
2. **加固路线图欠账在册**：12.4 S1-S9 中近期四项（S1/S2/S3/S4）与度量项（S6）已在优化冲刺闭环，**S5（L2 语义判定）/S7（PII 扩容）/S8（词表运营）/S9（L3 分类器）与 G1 间接注入评估口径全部未排期**，其中 2026 年调研实证间接注入已现网化（USENIX Security '26 在野研究），项目恰有 HITL 工具链与 MCP 对外通道，风险面真实；
3. **平台层安全配置存在盘点新发现的缺口**（本次代码级盘点首次确认，见 2.2 E7/E8），与 AI 护栏互补，宜一并收口。

**专项目标**：护栏体系从「L1 底线防御」（明文关键词拦截 + 软防线 + 度量门禁）升级为「**规则层全副武装（词表工程化 + 结构化模式 + 输出面扩充）+ 平台层零缺口 + 间接注入运行时闭环 + 语义层初建（L2）+ 运营与对抗可持续**」的形态，对齐 OWASP LLM Top 10 (2025) 三层防御路线的 L1 完全体 + L2 落地。

## 三、调研实证（六路，2026-08）

### 3.1 标准框架：OWASP 三清单格局

- [OWASP LLM Top 10 (2025)](https://genai.owasp.org/llm-top-10/) 中 **LLM01 Prompt Injection 连续两版居首**；[LLM01:2025 条目](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)给出的缓解组合为：约束模型行为与输出格式、输入输出过滤、**权限控制（模型最小权限 + 敏感动作人工确认）、外部内容与指令区隔离**；
- [OWASP LLM Prompt Injection Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html) 收录的技术族：提示隔离/聚光灯标记、金丝雀令牌（泄露探测，低成本低误报）、特权分离、编码变换检测；业界解读见 [Crisis of Agency 分析](https://gregrobison.medium.com/the-crisis-of-agency-a-comprehensive-analysis-of-prompt-injection-and-the-security-architecture-of-d274524b3c11)与 [10 项防御技术综述](https://aipromptarchitect.co.uk/guides/prompt-injection-prevention)；
- 攻击面已扩至 Agent 与工具协议：[OWASP Agentic AI Top 10](https://infosecwriteups.com/owasp-top-10-for-agentic-ai-applications-vs-top-10-owasp-llm-genai-security-risks-the-ultimate-81420b921d94)（自主体特有风险）与 [OWASP MCP Top 10](https://cycode.com/blog/owasp-mcp-top-10/)（令牌管理失当、工具投毒、影子服务器等）相继成稿——**项目双链 + HITL + MCP 形态恰好横跨三个清单的适用域**。

**项目采纳**：本专项按「过滤 + 隔离 + 权限 + 可观测」四象限组织功能点；金丝雀令牌纳入输出面（A3）；MCP 治理纳入平台层（B3）。

### 3.2 护栏方案格局：三层共识与「没有免费午餐」

- 2026 年方案横评（[MorphLLM 失效分类学与库对比](https://www.morphllm.com/llm-guardrails)、[Best AI Guardrails 2026](https://generalanalysis.com/guides/best-ai-guardrails)、[开源 vs 商业 12 方案对比](https://cloudthrill.ca/llm-guardrail-solutions)、[NeuralTrust 22k 样本基准报告](https://neuraltrust.ai/blog/neuraltrust-ai-security-model-performance-report-2026)）收敛出三层共识：**规则层（关键词/正则，快而确定，管已知明文形态）+ 分类器层（Llama Guard / Prompt Guard / Azure Prompt Shields / Bedrock Guardrails 类，管语义化载荷）+ 最小权限与流程控制（兜底）**；
- [《No Free Lunch With Guardrails》(arXiv)](https://arxiv.org/html/2504.00441v2) 实证：**不存在拦截率与误伤率双赢的护栏**——词表扩面必然伴随误伤面扩大，故扩充必须以干净语料零误伤门禁对冲，且语义层只做可疑触发不做全量；
- 分类器部署形态调研：本地 GPU 部署（Llama Guard 系）与 SaaS API（Azure/AWS/Lakera）两型；**ECS 2 核无 GPU 约束下本地型否决**（与 12.4 S9 裁决一致），API 型留长期登记。

**项目采纳**：L1 规则层做满（词表工程 + 结构化正则）→ L2 用既有备用模型 few-shot 二判（可疑触发）→ L3 维持「视资源」登记；FLAG 观察档与干净集门禁是「没有免费午餐」的工程对冲（A1/A4）。

### 3.3 间接注入：从 PoC 到在野利用，防御有实证有效手段

- 在野证据：[USENIX Security '26 间接注入在野研究](https://www.usenix.org/system/files/conference/usenixsecurity26/sec26_prepub_chang.pdf)、[社会 Web 语料 RAG 注入基准 (arXiv)](https://arxiv.org/html/2601.10923v2)、[RAG-Enabled Agent 多层防御基准 (arXiv)](https://arxiv.org/html/2511.15759v1)——检索文档载荷已是现实攻击通道；
- 有效防御手段谱系：① **聚光灯三式**（分隔符界定/数据标记/编码变换，[Microsoft 论文 (arXiv)](https://arxiv.org/abs/2403.14720)，[MSRC 多层防御实践](https://www.microsoft.com/en-us/msrc/blog/2025/07/how-microsoft-defends-against-indirect-prompt-injection-attacks)）——项目 S2 不可信数据区包裹即分隔符界定形态；② **CaMeL 能力分离**（[DeepMind 论文 (arXiv)](https://arxiv.org/abs/2503.18813)、[Simon Willison 解读](https://simonwillison.net/2025/Apr/11/camel/)）——以系统设计换取可证明安全，AgentDojo 77% 任务完成率 vs 无防御 84%，代价是能力受限，**适合工具执行域而非问答域**；③ 运行时对检索内容二次检测（[Lasso RAG Security 2026 实践](https://www.lasso.security/blog/rag-security)、[领域指南](https://futureagi.com/blog/what-is-prompt-injection-defense-2026/)）。

**项目采纳**：S2 已对齐①的分隔符形态；本专项补③的运行时扫描与打标消费（D1/D2）；CaMeL 式能力分离与项目 HITL 审批形态部分同构（写操作人工确认即能力门控），不引入其完整框架，登记在案；评估口径按 12.6 提案实施（D3）。

### 3.4 对抗测试自动化：四大开源框架

### 3.5 中文 PII 生态：Presidio 语义 + 中文自定义识别器

- [Microsoft Presidio](https://developer.cloud.tencent.com/article/2683680) 是事实标准架构（识别器注册表：正则/词表/NER 三类识别器 + 置信度 + 优先级），但本体为 Python 生态且默认分类以英文为主（[Wavect 生产对比](https://wavect.io/zh/blog/pii-redaction-before-llm-prompts/)）；
- 中文扩展先例：[zh_PII（Presidio 中文场景扩展）](https://github.com/ltm920716/zh_PII)、[cn_pii_anonymization](https://github.com/neednlab/cn_pii_anonymization)——**验证「确定性正则先行（身份证/银行卡/车牌/手机）、NER 类（姓名/地址）谨慎后置」的路线**；
- 项目为 Java 21 栈，ECS 2 核不承载 Python sidecar：**Java 原生按 Presidio 识别器注册表语义自建**（C2），不引入跨语言依赖；银行卡号须带 Luhn 校验防长数字串误报（延续 v2.4 边界断言纪律）。

## 四、功能实现点

> 编号规则：A=词表工程与输出面 · B=平台层加固 · C=PII 扩容 · D=间接注入运行时 · E=L2 语义层 · F=词表运营 · G=对抗自动化。每项标注对应缺口与 12.4 任务血缘。

### 4.1 A 组：词表工程化与检测面扩充（E1/E2，用户明确动因）

**A1 词表独立配置与结构化**（0.5d）
- 注入词表与输出词表自 yml 单行 CSV 抽为独立结构化配置文件（classpath `guardrail/injection-rules.yml` / `output-rules.yml`，支持外部路径覆盖）；词项模型：`id / family（攻击族）/ lang / type（KEYWORD|REGEX）/ value（编码态，见第七节）/ action（BLOCK|FLAG）/ enabled`；
- **攻击族系七分法**（参照 OWASP LLM01 缓解域与 3.2 失效分类学）：指令覆盖 / 角色劫持 / 敏感信息套取 / 编码混淆 / 多语种 / 越狱引导 / 工具诱导；
- **FLAG 观察档**：命中只计数 + 审计标记不拒绝（`rag.guardrail.flagged` 新指标）——新词先 FLAG 观察、零误伤后转 BLOCK，是词表扩面的误伤对冲机制（3.2「没有免费午餐」）；
- 三源合并语义：内置默认 + 结构化文件 + 既有 CSV 环境变量（`rag.guardrail.input.injection-keywords` 兼容保留），ETL 入库扫描与对话链同源消费（单一词表口径不变）。

**A2 注入检测面扩充**（1.5d）
- 干词三向扩充：中文同族变体（沿 v2.38 修正的补强方法）、英文与多语种高频干词（日韩法西俄等）、按族系补齐；目标规模干词 14 → 80-120，七族全覆盖；
- **新增 REGEX 结构化模式轨**（type=REGEX）：动词×宾语组合句式（覆盖「覆盖类动词 × 指令类宾语」「套取类动词 × 系统配置类宾语」等组合面）与编码特征模式——以模式代替字面样本枚举，大幅扩面同时天然遵守第七节纪律；目标 10-20 条；
- 误伤铁律延续：领域裸词不入 BLOCK 档（v2.38「裸领域词不入表，off-topic 由空证据拒答承接」原则）；可疑干词一律先 FLAG；
- kb-eval 联动：injection-qa.json 随族系同步扩面，GoldenDatasetLoaderTest 编程式自洽校验契约延续（门禁子集归一后必命中、编码样本归一前必不命中）。

**A3 输出检测面扩充**（1d）
- 输出词表分类化：业务保密 / 合规敏感 / 竞品对比 三类起步，各分类独立 action 与指标子项（替换现有 2 条占位）；
- **系统提示金丝雀校验**（调研：OWASP Cheat Sheet / Rebuff 金丝雀技术，低成本低误报的泄露确证手段）：系统提示内嵌随机金丝雀标记（启动时生成），OutputGuardrailAdvisor 聚合后验阶段校验输出是否回显 → 命中即确证提示泄露，整段替换 + 独立指标 `rag.guardrail.output.canary`；
- 输出 PII 回显探测（依赖 C 组识别器注册表）：回答中检出未掩码强形态 PII（如银行卡号）→ FLAG 观察起步，验证误报后再定动作。

**A4 词表质量门禁**（0.5d）
- 干净回归集：Golden 146 正常问题 + 少量审计干净样本构成，门禁口径 = BLOCK 档**零命中**，进 kb-eval 报告「安全性」小节强制项；
- 词表变更流程定案：新增 → FLAG 观察（指标 + 审计可查）→ 零误伤确认转 BLOCK——运营通道由 F 组承接。

### 4.2 B 组：平台层加固零缺口（E7/E8，盘点新发现）

### 4.3 C 组：PII 扩容与识别器注册表化（E4，12.4 S7 落地形态）

- **C1 确定性正则批扩容**（1d）：银行卡号（Luhn 校验 + 分隔符容忍 + 边界断言）、座机号、车牌号、IPv4 地址——四类全正则可判定，对话链掩码 + ETL 入库消毒同源生效（TextSanitizer 单一实现源纪律不变）；
- **C2 识别器注册表重构**（1.5d）：TextSanitizer 的 PII 能力演进为 `PiiRecognizer` 注册表形态——每类型独立识别器（模式 + 置信度 + 掩码策略 + enabled 开关 + 指标子项），对齐 Presidio 语义契约（3.5 调研定案：Java 原生自建，不引 Python 依赖）；配置族 `rag.guardrail.pii.{type}.enabled`；
- **C3 弱信号类型登记**：姓名/地址（NER 依赖，误报管理成本高——S7 原注记与调研一致）默认关闭，配置开关预留；待干净集误报度量后再评估，不排期。

### 4.4 D 组：间接注入运行时闭环与度量实证（E3，12.4 G1 收尾）

- **D1 运行时扫描与逐条警示**（1.5d）：证据注入 grounding 前对每个召回 chunk 跑 TextSanitizer 检测视图（复用注入词表——A 组扩面直接增益此防线）；命中 → 该条证据在模板中追加逐条警示注记（S2 是统一声明，此为逐条定位强化）+ 指标 `rag.guardrail.indirect.flagged` + 策略可配 `warn`（默认）/ `exclude`（剔除该 chunk）；正则层开销可忽略（每请求 topK 条扫描，毫秒级）；
- **D2 入库打标消费**（1d）：检索侧对 `injection_hit=true` chunk 降权（RRF 加权衰减形态）——**默认关闭**，先经 kb-eval 检索门禁（Recall/MRR）度量影响再决定开关口径；
- **D3 间接注入评估口径实施**（1.5d，12.6 提案落地，不等 S5）：毒化语料构造（3-5 篇植入载荷文档，载荷按第七节编码纪律制作与存储）+ LLM-as-Judge 判定回答是否执行注入指令（vs 忠于证据）+ 抑制率指标（S2 模板 + D1 逐条警示联合度量）；首跑基线入档，成为后续 L2/L3 增益的对照系。

### 4.5 E 组：L2 语义判定层（E6，12.4 S5 落地形态）

- **E1 可疑触发 LLM 二判**（3d）：
  - 触发条件：结构化模式可疑（A2 REGEX 轨评分）且干词未命中——非全量（3.2 共识：全量判定成本不划算且误伤面大）；
  - 实现：复用备用模型（qwen3.7-plus 百炼端点）few-shot 分类，输出 PASS/SUSPECT/BLOCK；BLOCK → PROMPT_INJECTION 同语义拒答；SUSPECT → FLAG 计数放行；
  - 装配：新 SemanticInjectionAdvisor **order 320**（L1 300 之后、记忆 400 之前——确保 L2 拒绝内容不入多轮记忆），双链装配；
  - 容错：LLM 调用失败/超时（≤3s）fail-open 回落 L1 结论（无命中不拒绝），指标 `rag.guardrail.l2.error`；成本口径：预计触发 <5% 请求，指标跟踪；
  - 多阶段注入信号（调研：2026 主流攻击模式之一）：跨轮结构模式共现作为扩展触发信号，首期实现简单规则（近 N 轮记忆拼接视图跑 REGEX 轨），深度上下文判定登记不排期。
- **E2 门禁口径演进**（1d）：E1 稳定后 JAILBREAK/MULTILINGUAL 观察集升格门禁子集（门禁防域 = L1+L2 联合），阈值首版 ≥90% 起步（G1 对抗语料校准基线后调）；kb-eval 报告「安全性」小节扩「L1 单独 / L1+L2 联合」双读数。

### 4.6 F 组：词表动态运营（E5，12.4 S8 适配 4.7 Git Ops 定案）

- **F1 Git Ops 词表运营**（1.5d）：词表文件以 Git 为单一事实源（git log = 版本历史，与 4.7 Prompt 模板 Git Ops 定案同款，**不建 DB+Redis 持久化的原 S8 形态**——单开发者场景过度设计）；热更新 = Redis pub/sub 信号触发重载（失败回落 mtime 轮询），攻击情报响应免重启；
- **F2 kb-admin 词表管理端点**（1d）：词表列表查询（族系/语种/动作/启用态过滤）+ 命中演练端点（输入文本 → 返回将命中词项与 action，演练不计指标不落审计）——为 A4「FLAG→BLOCK 转档」提供运营视图。（2026-08-19 注记：前端第五 Tab 落地消费本端点；词表运营形态再评估定案维持 Git Ops，Plan C DB 化复审触发条件钉死，见 12 章 v2.52）

### 4.7 G 组：对抗自动化与语料扩容（度量纵深）

- **G1 红队工具引入**（1.5d）：Promptfoo 首选（3.4 定案）——HTTP Provider 对接本项目 chat 端点，配置化广扫（注入/越狱/信息套取场景模板），离线按需/每周跑，报告入档 `docs/project-progress/`；Garak 作一次性全面体检备选；工具产出载荷一律按第七节编码化入库；
- **G2 攻击语料扩容 48→100**（1d）：新增族系样本（工具诱导 / 间接注入对话触发 / 多语种扩面 / 同义改写变体），DIRECT/ENCODING 门禁子集同步扩面，自洽校验契约不破；红队工具产出的高价值变体经编码化后择优入集。

> 沿用「2-3 关联点成簇」纪律：每簇 = 实现 → 验证 → 文档回写 → 提交闭环；验证不过不进下一簇。专项簇序以「安全簇」冠名，与 Phase 4 七簇编号空间隔离。

|---|---|---|---|---|---|

**合计约 18-23.5 人日（≈4-5 周）**。压缩预案：安全⑤的 E2 门禁演进可拆尾批、安全⑥的 G1 可降级为一次性体检。

### 5.2 顺序理由

- **安全①先行**：用户明确动因；且 A2 的 REGEX 可疑信号是安全⑤的触发源、A1 的结构化词表是安全④运行时扫描与安全⑥运营的前置——一词表而三下游；
- **安全②插入早段**：平台层缺口与 AI 护栏解耦、体量小、独立可验，趁盘点记忆新鲜收口；B4 的 ECS 安全组项与顺延的 Phase 4 簇⑥（生产加固）天然协作，届时顺带；
- **安全③居中**：独立性最强（不依赖不阻塞），位置可与安全④互换；
- **安全④在安全①后**：D1 扫描消费 A 组扩面后的词表，先扩面后闭环收益最大；
- **安全⑤靠后**：依赖安全①信号与安全④基线，且引入新 Advisor 与新成本面，待规则层做满后再上语义层（S5 原排期原则「视攻击面暴露」由 D3/G1 的度量数据支撑决策）；
- **安全⑥压轴**：运营与对抗是专项可持续性的收口件，红队扫描在全部防线就绪后跑才有完整读数。

### 5.3 每簇 DoD（沿用优化冲刺口径）

1. 代码 + 单测绿（涉及模块 `mvn -q --no-transfer-progress test`，kb-eval 门禁复跑不破）；
2. 验证通道通过，证据落进度文档任务行；
3. 文档回写：进度文档 + 设计回写（第六节清单）+ CLAUDE.md 同步；
4. git 提交（一功能一提交，代码 + 文档同批）；
5. **附加**：全部产出物通过第七节敏感词纪律自检。

## 七、专项约束：敏感词交付纪律（全程强制）

> **背景**：词表扩充与攻击样本必然承载攻击性语料；若以字面明文落入仓库文件，后续 AI 辅助会话读取时将触发上游注入检测，导致请求被拒（400 block）且上下文污染（后续消息持续被拒）。v2.38 既有样本为温和形态尚未触发，扩面后风险实质上升。本纪律适用于本专项全部产出物（方案/代码/配置/语料/文档/E2E 步骤）。

1. **文档与方案零字面载荷**：攻击内容一律以族系名 / 结构描述 / 样本 ID 引用表达，不引用字面载荷文本（本方案即为示范）；
2. **词表与攻击样本编码化存储（推荐定案方向）**：词项 value 与新增样本 question 以逐条 Base64（或等价转义形态）存储，加载层解码消费；单测自洽校验消费解码态；存量 48 条明文样本随安全①同批迁移，加载器过渡期双形态兼容。**定性说明**：编码不是安全机制（词表对攻击者无保密意义），纯为交付形态约束——防 AI 辅助链路误检测；
3. **配置键 / 指标名 / 类名纪律**：命名不含攻击语义字面（族系用中性枚举名，如 INSTRUCTION_OVERRIDE）；
4. **E2E 步骤文档**：载荷验证以「使用编码样本 {id}」描述，不粘贴字面内容；用户自测时由工具/脚本解码注入，不经文档传递；
5. **红队工具产出**：G1/G2 承接的第三方语料先编码化再入库，禁止明文转录。
