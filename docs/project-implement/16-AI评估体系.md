## 16.1 Golden Dataset

```java
/**
 * Golden Dataset —— 自动化评估的标准问答对
 * 版本化管理在 Git 中（kb-eval/src/main/resources/golden/*.json）
 */
public record GoldenQAPair(
    String id,
    String question,                  // 测试问题
    String expectedKeywords,          // 期望包含的关键词（宽松匹配）
    String expectedAnswer,            // 理想回答（LLM-as-Judge 严格评分用）
    List<String> expectedChunkIds,    // 期望命中的 Chunk ID（chunk 级检索指标用；确定性 ID，9.3 v2.22）
    List<String> expectedDocs,        // 期望命中的文件名（文档级兜底检索指标用，v2.21）
    String category,                  // 事实查询 / 推理 / 表格 / 多文档 / 多跳 / 负向 / 注入
    boolean negative                  // true = 知识库外问题（Negative Rejection 用例）
) {
    public static List<GoldenQAPair> loadFromJson(String path) { /* ... */ }
}
```

**构建要求**：

- 分类覆盖：事实查询、跨段落推理、表格数据、多文档聚合、**多跳推理（MULTI_HOP，簇④：答案须经实体链跨片段/跨文档推理得出，机器侧草稿 + 人工审定工作流，见本章头 v2.71）**、**负向用例（库外问题，≥20%，对齐 RAGAS/LlamaIndex 评测实践）**；
- 专有名词专项子集：标题词、字段名、课程名、产品型号各 10+ 条（对应"专有名词命中率 > 90%"验收）；
- `expectedChunkIds` 由人工标注 + 检索调试台（10.7）辅助验证；
- Phase 5 引入合成生成（LLM 基于 Chunk 生成候选问答对 → 人工审核），加速扩充至 200+。

## 16.2 指标体系（v2 扩充）

### 检索质量（Retrieval）

| 指标 | 定义 | 计算方式 | 目标 | 期 |
|------|------|---------|------|---|
| **Top-K Recall** | Top-K 是否包含正确回答所需 Chunk | expectedChunkIds 命中率 | > 90% | Phase 2 |
| **MRR** | 首个相关 Chunk 的倒数排名均值 | Mean Reciprocal Rank | > 0.8 | Phase 2 |
| **Context Precision** | Top-K 中相关 Chunk 的占比（排名加权） | RAGAS 定义 | > 0.75 | Phase 2 |

### 生成质量（Generation）

| 指标 | 定义 | 计算方式 | 目标 | 期 |
|------|------|---------|------|---|
| **Faithfulness** | 回答忠于检索上下文（无幻觉） | LLM-as-Judge (1-5) | > 4.5 | Phase 2 |
| **Response Relevancy** | 回答切题程度（RAGAS 原 Answer Relevancy，2026 已更名） | LLM-as-Judge (1-5) | > 4.0 | Phase 2 |
| **Answer Correctness** | 回答正确性 | 关键词匹配 + LLM-as-Judge | > 85% | Phase 5 |
| **Citation Attribution** | [ref-N] 引用可解析且来源支撑声明 | 三步验证（CiteGuard 框架：发出引用→可解析→来源支撑） | > 90% | Phase 5 |

### 鲁棒性（v1 完全缺失，v2 补齐）

| 指标 | 定义 | 计算方式 | 目标 | 期 |
|------|------|---------|------|---|
| **Negative Rejection** | 库外问题正确拒答（而非编造） | negative 用例的规范拒答率 | > 90% | Phase 2（建基线） |
| **Injection Block Rate** | 注入攻击拦截率（L1 防域子集） | INJECTION 门禁子集（DIRECT+ENCODING_BYPASS）的 BLOCKED 占比（v2.24，簇⑤ B2 S6） | ≥ 95% | Phase 2（v2.24 落地门禁） |
| **Injection Block Rate（L1+L2 联合）** | L2 防域子集判别率 | 力判联合链对 L1 未拦样本逐条判定，JAILBREAK+MULTILINGUAL 子集 BLOCKED 占比（v2.25，安全簇⑤ E2；默认关 `eval.guardrail.l2-enabled`） | ≥ 90%（首版从宽） | 安全簇⑤（v2.25 落地门禁） |
| **Indirect Injection Suppression** | 间接注入抑制率 | Judge EXECUTED/RESISTED 打分位，RESISTED 占比（v2.25，安全簇④ D3；默认关 `eval.indirect.enabled`） | 建基线（首跑 1.000） | 安全簇④（v2.25 落地） |
| **Noise Robustness** | 检索混入无关 Chunk 时不被误导 | 注入噪声 Chunk 前后答案一致率 | > 85% | Phase 5 |
| **Hallucination Rate** | 无证据声明占比（含压力场景） | LLM-as-Judge 声明级核查 | < 5% | Phase 5 |

> **框架对应**：检索与生成指标与 RAGAS 指标集对齐（可直接用 RAGAS 定义做交叉验证）；工程化 CI 集成采用 pytest 风格的 DeepEval 或自研 EvalRunner（16.5）。Java 侧评估执行器负责取数（调检索调试 API + 对话 API），评分可调用 LLM-as-Judge API。
>
> **Phase 5 四指标实现状态（v2.67，簇② 5.8 批1）**：上表四项 Phase 5 指标已全部落地 `kb-eval`（观察带——只报告不门禁，见章首 v2.67 注记与 §16.4 阈值表预留行）。实现要点：Answer Correctness 依赖 `expectedAnswer` 标注（**当前语料零标注 → 读数待标注批**，Bad Case 回灌通道已支持该字段）；Citation Attribution 三步中前两步为确定性判定（`CitationMetrics`：`[ref-N]` 提取 + 编号范围校验），未过即判负免 Judge；Noise Robustness 为抽样制（缺省关），噪声证据经编号续接混入、评估侧用同一基座 + 同一 GROUNDING_PROMPT 生成对照答案；Hallucination Rate 为声明级核查（0-100 百分比换算 0-1 比率）。
>
> **人类校准通道（v2.68，簇② 批2）**：观察带的定档机制——`eval.judge-agreement-sample`（批5 复跑置 50）触发五维校准表双通道（材料 MD + 打分 CSV，human_a/human_b 正交双标注），人工回填后经 `--eval.calibration-readback=<csv>` 回读逐维 Cohen's κ 三对（Judge×A / Judge×B / A×B），对照 `eval.calibration.kappa-target=0.80` 判 PASS/FAIL——**κ≥0.80 是四新指标接入门禁的前置判据**。标度口径：F/AC 序数 1-5 走二次加权 κ；CA/HR/NRob 名义二分类（CA 无引用判负、HR 比率 >0 二值化、NRob A/B 一致性）。AC 读数前置的 `expectedAnswer` 标注定案「机器侧草稿 + 人工审定」：`--eval.draft-answers` 以 golden 标注 chunk 真值（PG 直查，零循环）起草理想回答，人工审定回写语料后 AC 才有样本。κ 达标前观察带维持「只报告不门禁」不变。

## 16.3 LLM-as-Judge 规范（v2 新增）

2026 年 LLM-as-Judge 是企业评估 mainstream，但有明确的使用纪律：

1. **Judge 模型与被测模型隔离**：被测为 DeepSeek V4，Judge 用另一厂商模型（如 qwen3.7-plus），避免 self-preference 偏差；
2. **三类偏差必须处理**：长度偏差（长答案易得高分）、模型家族偏差、位置偏差（多候选对比时）——评分 prompt 采用 G-Eval 式 CoT 评分（先推理后打分），成对比较时随机化顺序；
3. **人类校准**：Phase 5 完成 judge 与人工标注的一致率校准，目标 **85-90%**；低于 80% 的指标不进入 CI 门禁，仅作参考；
4. **混合评估栈**：LLM-as-Judge + 规则校验（关键词/引用可解析性/JSON 结构）+ 人工抽检（每周 Bad Case 队列），不能只靠 Judge。

## 16.4 CI 评估门禁（v2 新增）

```
PR 触及 prompt 模板 / 检索参数 / Advisor 链 / 切分策略
    │
    ▼
CI 触发 EvalRunner（kb-eval，profile=ci）
    │
    ├── 检索指标：Top-K Recall / MRR / Context Precision（确定性计算，无 LLM 成本）
    ├── 生成指标：Faithfulness / Response Relevancy（LLM-as-Judge，采样 30 条控成本）
    └── 负向：Negative Rejection 全量
    │
    ▼
评分 < 阈值（或较 main 分支基线回归 > 3%）→ 阻断合并
评分报告 → Langfuse dataset run 记录（可追溯每次变更的效果曲线）
```

> **v2.20 修正（2026-08-12，簇④ E1 Judge 校准基建）**：
> 1. **Faithfulness 容忍策略**（针对 4.093 贴线的噪声防线）：门禁由「均值 ≥ 阈值」升级为「**均值 ≥ 阈值 − 容忍带** 且 **单维不崩**」。噪声带 `eval.thresholds.faithfulness-tolerance`（默认 0.05）——均值 ∈ [3.95, 4.0) 记 WARN 放行，低于 3.95 才判真实击穿；分类均值地板 `faithfulness-category-floor`（默认 3.5）——整体均值可能被大类拉高掩盖单一分类崩盘，任一正向分类均值低于地板即失败（样本数 ≥ `faithfulness-category-min-samples` 默认 3 才检查，防小样本噪声）。「单维」实现口径 = Golden 用例分类（FACTOID/REASONING/TABLE/MULTI_DOC）。
> 2. **校准复跑快照**：`eval.run-label` 非空时报告落盘 `eval-report-{label}.txt`——Judge thinking 开/关复跑、A/B 基线各留独立文件，防互覆。

## 16.5 EvalRunner 执行器

```java
package com.enterprise.kb.eval.runner;

/**
 * 评估执行器 —— 取数（检索/对话 API）+ 评分 + 报告
 *
 * <p>运行模式：
 * - CI 模式（profile=ci）：启动即跑，低于阈值抛 EvalFailedException 使构建失败；
 * - 手动模式：Admin API 触发，报告写 Langfuse + 落 kb_audit_log 备查。</p>
 */
@Component
public class EvalRunner {

    private final ChatClient chatClient;                    // 被测链路
    private final RetrievalDebugClient retrievalDebug;      // 10.7 检索调试 API
    private final LlmJudgeClient judge;                     // 16.3 Judge 模型
    private final List<GoldenQAPair> goldenDataset;

    @EventListener(ApplicationReadyEvent.class)
    public void runEvalIfCiProfile() {
        if (!"ci".equals(activeProfile)) return;
        EvalReport report = runFullEval();
        // 阈值来自 application-eval.yml（16.4 门禁阈值表），此处为示意
        if (report.topKRecall() < thresholds.topKRecall()
                || report.faithfulness() < thresholds.faithfulness()
                || report.negativeRejection() < thresholds.negativeRejection()) {
            throw new EvalFailedException("评估低于阈值: " + report.summary());
        }
    }

    private EvalReport runFullEval() {
        List<EvalResult> results = goldenDataset.stream().map(qa -> {
            // 检索侧：Top-K 中是否命中 expectedChunkIds + 排名
            var retrieval = retrievalDebug.search(qa.question(), 5);
            double recall = retrieval.hitRecall(qa.expectedChunkIds());
            double rr = retrieval.reciprocalRank(qa.expectedChunkIds());

            // 生成侧
            String answer = chatClient.prompt().user(qa.question()).call().content();
            double faithfulness = qa.negative()
                ? scoreRejection(answer)                        // 负向用例：是否规范拒答
                : judge.scoreFaithfulness(answer, retrieval.contents());
            return new EvalResult(qa, retrieval, answer, recall, rr, faithfulness);
        }).toList();
        return new EvalReport(results);
    }
}
```

> **A/B 双跑差异通道（v2.69，簇② 批3）**：基于 Prompt Git Ops（4.8）——prompt 版本即
> git 版本，双跑 = 两个 git 版本各跑一轮全量评估，不新建抽象层。工作流：
> ① `EVAL_RUN_LABEL=baseline` 全量跑 → 快照 `eval-results-baseline.json` 随报告落盘；
> ② 切换候选版本（git 切换 / prompt 改动）`EVAL_RUN_LABEL=candidate` 复跑；
> ③ `--eval.diff=baseline,candidate` 产出差异报表 `eval-diff-baseline-candidate.md`
> （零 LLM 调用，工具模式豁免全量评估）。可比性三前提钉死：① 锚点可回溯（报告头
> git 哈希 + 提交时间 + 运行时刻，工作区脏 ⚠ 显式——脏工作区的哈希不完全代表运行
> 代码）；② 配置一致（探针/抽样/Top-K/检索-only/Judge 模型·温度·思考/Phase 5 开关/
> NRob 抽样/护栏 L2 逐项核验，失配即混杂因素 ⚠）；③ 用例集一致（golden 语料漂移
> 单独告警）。差异判定消费 `eval.thresholds.regression` 容忍带（0.03，16.4 预留位
> 于此接线）：超带判 IMPROVED/REGRESSED（Hallucination Rate 方向反语义），带内
> STABLE，任一侧无样本判样本缺失不计成败。**内容盲纪律**：快照与报表只含用例 ID、
> 数值、verdict 与计数；答案变化经 SHA-256 指纹比对检出（「是否变了」可度量，
> 正文不经机读面传播）。观察面报表不入门禁——A/B 结论以单变量为前提。

### 16.6.1 反馈微调数据导出管道（v2.70，簇② 批4，5.10 收窄版）

> **落地形态**：kb-admin `FeedbackExportService` + `FeedbackExportAdminController`
> （kb-api fat jar 聚合，禁反向依赖纪律不变）——HTTP 附件下载，纯读旁路
> （不改变反馈/审计任何状态）；机器侧先行，本批不含前端按钮。
>
> **端点清单**（租户守卫同簇③/④：owner claim → tenantId，缺失 fail-closed
> IDENTITY_INCOMPLETE）：
> - `GET /api/v1/admin/feedback/export/summary`——导出概览（dry-run）：双格式
>   可导出计数 + 跳过原因分解（会话材料不全 / 审计非 SUCCESS / 👎 未附期望回答）+
>   PII 掩码命中数 + 百炼门槛对照（SFT≥100 / DPO≥50 对，只报告不阻断）
> - `GET /api/v1/admin/feedback/export?format=sft|dpo`——JSONL 附件
>   （`application/x-ndjson`，文件名 `kb-feedback-{format}-{tenant}-{date}.jsonl`，
>   租户 ID 入文件名前安全化）
>
> **双格式派生规则（确定性）**：
> - SFT 采纳通道：👍 反馈 →（问题，系统原回答）单轮对；
> - SFT 订正通道：👎 且附 expectedAnswer →（问题，用户期望回答）；
> - DPO 偏好对：👎 + expectedAnswer + 原回答齐备 → 同一问题下 chosen=用户订正 /
>   rejected=系统原回答——二元反馈天然成对，无需跨会话同题配对（后者需问句模糊
>   匹配，本批不引入，登记为扩展点）。
>
> **质量三重过滤**：① 审计三态联查（经 3.17 回填的 audit_log_id）——REJECTED/ERROR
> 结局的对话不入训练材料（护栏替换话术/异常响应无训练价值），审计行缺失
> （关闭或未落）不阻断导出；② PII 消毒——问题/原回答/期望回答三字段经共享
> `PiiRecognizerRegistry` 同一 Bean 掩码（对话链/ETL/审计同款，训练数据不携
> PII 明文）；③ 会话材料完整性——问题经时间序最近 USER 消息解析
> （同 3.17 Bad Case 查询口径），不可解析跳过。
>
> **格式参考（不绑定平台）**：对齐百炼调优数据上传规则的 ChatML 形态——
> SFT `{"messages":[{user},{assistant}]}`（**不烘焙 system**：grounding 提示词
> 按请求注入，烘焙入训练数据会与 prompt 版本耦合，送训侧自行前置）；
> DPO `{"messages":[{user}],"chosen":{assistant},"rejected":{assistant}}`。
> 逐行 \n 结尾，顺序按反馈 createdAt 正序确定性稳定（跨导出可比）。
>
> **数据量纪律**：门槛为百炼通道建议线，非系统门禁——「导出 ≥200 例双格式」
> 验收计数在簇② 批5 用户侧复跑窗口执行；不足是数据量问题不是缺陷，如实报告。
