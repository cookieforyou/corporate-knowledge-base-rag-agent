## 16.1 Golden Dataset

```java
/**
 * Golden Dataset —— 自动化评估的标准问答对
 * 版本化管理在 Git 中（kb-eval/src/main/resources/golden/*.json）
 */
public record GoldenQAPair(
    String id,
    String question,                  // 测试问题
    String expectedKeywords,          // 期望包含的关键词（宽松匹配）
    String expectedAnswer,            // 理想回答（LLM-as-Judge 严格评分用）
    List<String> expectedChunkIds,    // 期望命中的 Chunk ID（chunk 级检索指标用；确定性 ID，9.3 v2.22）
    List<String> expectedDocs,        // 期望命中的文件名（文档级兜底检索指标用，v2.21）
    String category,                  // 事实查询 / 推理 / 表格 / 多文档 / 负向
    boolean negative                  // true = 知识库外问题（Negative Rejection 用例）
) {
    public static List<GoldenQAPair> loadFromJson(String path) { /* ... */ }
}
```

**构建要求**：

- 分类覆盖：事实查询、跨段落推理、表格数据、多文档聚合、**负向用例（库外问题，≥20%，对齐 RAGAS/LlamaIndex 评测实践）**；
- 专有名词专项子集：标题词、字段名、课程名、产品型号各 10+ 条（对应"专有名词命中率 > 90%"验收）；
- `expectedChunkIds` 由人工标注 + 检索调试台（10.7）辅助验证；
- Phase 5 引入合成生成（LLM 基于 Chunk 生成候选问答对 → 人工审核），加速扩充至 200+。

## 16.2 指标体系（v2 扩充）

### 检索质量（Retrieval）

| 指标 | 定义 | 计算方式 | 目标 | 期 |
|------|------|---------|------|---|
| **Top-K Recall** | Top-K 是否包含正确回答所需 Chunk | expectedChunkIds 命中率 | > 90% | Phase 2 |
| **MRR** | 首个相关 Chunk 的倒数排名均值 | Mean Reciprocal Rank | > 0.8 | Phase 2 |
| **Context Precision** | Top-K 中相关 Chunk 的占比（排名加权） | RAGAS 定义 | > 0.75 | Phase 2 |

### 生成质量（Generation）

| 指标 | 定义 | 计算方式 | 目标 | 期 |
|------|------|---------|------|---|
| **Faithfulness** | 回答忠于检索上下文（无幻觉） | LLM-as-Judge (1-5) | > 4.5 | Phase 2 |
| **Response Relevancy** | 回答切题程度（RAGAS 原 Answer Relevancy，2026 已更名） | LLM-as-Judge (1-5) | > 4.0 | Phase 2 |
| **Answer Correctness** | 回答正确性 | 关键词匹配 + LLM-as-Judge | > 85% | Phase 5 |
| **Citation Attribution** | [ref-N] 引用可解析且来源支撑声明 | 三步验证（CiteGuard 框架：发出引用→可解析→来源支撑） | > 90% | Phase 5 |

### 鲁棒性（v1 完全缺失，v2 补齐）

| 指标 | 定义 | 计算方式 | 目标 | 期 |
|------|------|---------|------|---|
| **Negative Rejection** | 库外问题正确拒答（而非编造） | negative 用例的规范拒答率 | > 90% | Phase 2（建基线） |
| **Injection Block Rate** | 注入攻击拦截率（L1 防域子集） | INJECTION 门禁子集（DIRECT+ENCODING_BYPASS）的 BLOCKED 占比（v2.24，簇⑤ B2 S6） | ≥ 95% | Phase 2（v2.24 落地门禁） |
| **Noise Robustness** | 检索混入无关 Chunk 时不被误导 | 注入噪声 Chunk 前后答案一致率 | > 85% | Phase 5 |
| **Hallucination Rate** | 无证据声明占比（含压力场景） | LLM-as-Judge 声明级核查 | < 5% | Phase 5 |

> **框架对应**：检索与生成指标与 RAGAS 指标集对齐（可直接用 RAGAS 定义做交叉验证）；工程化 CI 集成采用 pytest 风格的 DeepEval 或自研 EvalRunner（16.5）。Java 侧评估执行器负责取数（调检索调试 API + 对话 API），评分可调用 LLM-as-Judge API。

## 16.3 LLM-as-Judge 规范（v2 新增）

2026 年 LLM-as-Judge 是企业评估 mainstream，但有明确的使用纪律：

1. **Judge 模型与被测模型隔离**：被测为 DeepSeek V4，Judge 用另一厂商模型（如 qwen3.7-plus），避免 self-preference 偏差；
2. **三类偏差必须处理**：长度偏差（长答案易得高分）、模型家族偏差、位置偏差（多候选对比时）——评分 prompt 采用 G-Eval 式 CoT 评分（先推理后打分），成对比较时随机化顺序；
3. **人类校准**：Phase 5 完成 judge 与人工标注的一致率校准，目标 **85-90%**；低于 80% 的指标不进入 CI 门禁，仅作参考；
4. **混合评估栈**：LLM-as-Judge + 规则校验（关键词/引用可解析性/JSON 结构）+ 人工抽检（每周 Bad Case 队列），不能只靠 Judge。

## 16.4 CI 评估门禁（v2 新增）

```
PR 触及 prompt 模板 / 检索参数 / Advisor 链 / 切分策略
    │
    ▼
CI 触发 EvalRunner（kb-eval，profile=ci）
    │
    ├── 检索指标：Top-K Recall / MRR / Context Precision（确定性计算，无 LLM 成本）
    ├── 生成指标：Faithfulness / Response Relevancy（LLM-as-Judge，采样 30 条控成本）
    └── 负向：Negative Rejection 全量
    │
    ▼
评分 < 阈值（或较 main 分支基线回归 > 3%）→ 阻断合并
评分报告 → Langfuse dataset run 记录（可追溯每次变更的效果曲线）
```

**CI 门禁阈值表**（v2 新增，统一配置于 `application-eval.yml`，禁止散落在代码中）：

| 指标 | Phase 2 阈值（建基线期，从宽） | Phase 5 阈值（校准后） |
|------|------|------|
| Top-K Recall (K=5) | ≥ 0.85 | ≥ 0.90 |
| MRR | ≥ 0.70 | ≥ 0.80 |
| Faithfulness (1-5) | ≥ 4.0 | ≥ 4.5 |
| Negative Rejection | ≥ 0.85（建基线） | ≥ 0.90 |
| Injection Block Rate（门禁子集 DIRECT+ENCODING_BYPASS） | ≥ 0.95（v2.24，簇⑤ B2 S6） | ≥ 0.98（词表多语言扩容/S5 就位后议） |
| 较 main 基线回归幅度 | > 3% 阻断 | > 3% 阻断 |
| LLM-as-Judge 与人工一致率 | 仅记录不门禁 | ≥ 85% 方可门禁（16.3） |

Phase 2 期间阈值从宽（建基线），Phase 5 校准后收紧。

> **v2.20 修正（2026-08-12，簇④ E1 Judge 校准基建）**：

## 16.5 EvalRunner 执行器

```java
package com.enterprise.kb.eval.runner;

/**
 * 评估执行器 —— 取数（检索/对话 API）+ 评分 + 报告
 *
 * <p>运行模式：
 * - CI 模式（profile=ci）：启动即跑，低于阈值抛 EvalFailedException 使构建失败；
 * - 手动模式：Admin API 触发，报告写 Langfuse + 落 kb_audit_log 备查。</p>
 */
@Component
public class EvalRunner {

    private final ChatClient chatClient;                    // 被测链路
    private final RetrievalDebugClient retrievalDebug;      // 10.7 检索调试 API
    private final LlmJudgeClient judge;                     // 16.3 Judge 模型
    private final List<GoldenQAPair> goldenDataset;

    @EventListener(ApplicationReadyEvent.class)
    public void runEvalIfCiProfile() {
        if (!"ci".equals(activeProfile)) return;
        EvalReport report = runFullEval();
        // 阈值来自 application-eval.yml（16.4 门禁阈值表），此处为示意
        if (report.topKRecall() < thresholds.topKRecall()
                || report.faithfulness() < thresholds.faithfulness()
                || report.negativeRejection() < thresholds.negativeRejection()) {
            throw new EvalFailedException("评估低于阈值: " + report.summary());
        }
    }

    private EvalReport runFullEval() {
        List<EvalResult> results = goldenDataset.stream().map(qa -> {
            // 检索侧：Top-K 中是否命中 expectedChunkIds + 排名
            var retrieval = retrievalDebug.search(qa.question(), 5);
            double recall = retrieval.hitRecall(qa.expectedChunkIds());
            double rr = retrieval.reciprocalRank(qa.expectedChunkIds());

            // 生成侧
            String answer = chatClient.prompt().user(qa.question()).call().content();
            double faithfulness = qa.negative()
                ? scoreRejection(answer)                        // 负向用例：是否规范拒答
                : judge.scoreFaithfulness(answer, retrieval.contents());
            return new EvalResult(qa, retrieval, answer, recall, rr, faithfulness);
        }).toList();
        return new EvalReport(results);
    }
}
```

## 16.6 反馈闭环（Phase 3 采集 → Phase 5 闭环）

```
    │
    ▼

    │
    ▼

    └──→ 偏好数据导出（Phase 5.10：JSONL，chosen/rejected 对）

```

KTO（Kahneman-Tversky Optimization）天然适配 👍/👎 二元反馈，无需成对偏好数据，是本项目反馈闭环的首选微调方法。
