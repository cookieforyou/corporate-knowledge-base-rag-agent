## 14.1 Chunk 运维 API（4.4 定稿）

**模块落位**：kb-admin 首建——依赖 kb-etl（SanitizingTransformer / ChunkCleanupService /
EsIndexWriter / DocumentEtlService.vectorMetadata）+ kb-ai-core（AiBusinessMetrics）；
kb-api 经 Maven 依赖聚合进 fat jar（启动类 `scanBasePackages` 全域扫描零改动）。
kb-admin **不可反向依赖 kb-api**：重建能力经 `ReindexGateway` 接口倒置（14.2），
租户提取不复用 JwtUtils（本 Controller 直消费 Jwt principal）。

**租户守卫形态**：`@AuthenticationPrincipal Jwt` 直接消费 OAuth2 Resource Server 解析
结果，claim 映射同源 Casdoor 口径（`owner → tenantId`）；JWT 缺失 / owner 空白
fail-closed 抛 `IDENTITY_INCOMPLETE`（与既有 Controller 同款语义，单测直调覆盖）。

**端点**：`PUT /api/v1/admin/chunks/{chunkId}`（编辑）/ `DELETE` 同路径（软删）/
`POST /{chunkId}/restore`（恢复）。Chunk 列表查询**不新建端点**——复用
`GET /api/v1/documents/{id}/chunks`（观测台数据源，含所有权校验）。

**守卫序列（fail-closed）**：chunk 不存在 / 文档不存在 / 跨租户一律 `CHUNK_NOT_FOUND`
（不泄露存在性，同反馈域 MESSAGE_NOT_FOUND 语义）；所属文档处理中
（`DocumentStatus.isProcessing()` 三态）→ `DOC_NOT_READY` 409（防与在途 ETL 竞态互覆）；
软删 chunk 的编辑面不可见（CHUNK_NOT_FOUND，先恢复再编辑）；非软删 chunk 恢复
→ `CHUNK_NOT_DELETED` 409。

**编辑语义 = 运维补丁**：与 ETL 入库链**同源消毒**（SanitizingTransformer：PII 掩码 +
注入打标不阻断）→ PG 同步写 content / tokenCount / metadata（injection_hit 合并，
heading_path 等既有键保留）→ `etlExecutor` 异步重嵌入（向量 delete→add + ES indexChunks
覆写）。**chunk ID 不变**（确定性 ID 锚点，Golden 标注不因编辑失效）；后续
reparse/replace 以 MinIO 原件重走管线会覆写手工编辑（PG 事实源回归原件，设计行为）。
异步重嵌入失败仅告警不阻断——PG 事实源已更新，重建（14.2）兜底（9.4 一致性模型）。

**草图三处实证修正**（源码级核验定案）：
1. **重嵌入两步形态**：pgvector add 为 `INSERT ... ON CONFLICT DO UPDATE` 真 upsert，
   而 MilvusVectorStore add 为普通 insert（同 ID 重复写入无覆写保证）——统一
   **delete → add 两步**，双向量库后端同语义（chunkId == vectorId 不变量，9.3）；
   异步窗口内短暂检索缺失为运维操作可接受形态。
2. **`original_content` 语义**：草图当编辑备份错误——其义为「保护块原始 HTML /
   语境增强前原文」（确定性 ID 散列源与溯源载体），编辑不动它。
3. **异步提交形态**：草图 `@Async` 同类私有方法自调用不经代理不生效——改
   `@Qualifier("etlExecutor")` Bean 显式 `execute()`。

**软删 / 恢复**：软删委派 C1 管道 `ChunkCleanupService.softDelete`（PG is_deleted +
ES markDeleted + 向量物理删），已软删重复调用幂等（applied=false）；恢复 =
is_deleted=false 落 PG + 异步重嵌入（软删时向量已物理删，恢复必经重嵌入；ES 经
indexChunks 覆写复位 is_deleted=false）。

**指标**：`rag.chunk.edit / rag.chunk.soft.delete / rag.chunk.restore` 计数
（`recordChunkOps(operation)` 收口，零标签纪律防基数膨胀）。

```java
@RestController
@RequestMapping("/api/v1/admin/chunks")
public class ChunkAdminController {
    private final ChunkOpsService chunkOpsService;

    @PutMapping("/{chunkId}")   // 编辑：同源消毒 → PG 同步 → 异步重嵌入
    public ApiResponse<ChunkView> edit(@AuthenticationPrincipal Jwt jwt,
                                       @PathVariable String chunkId,
                                       @Valid @RequestBody ChunkUpdateRequest request) { ... }

    @DeleteMapping("/{chunkId}")              // 软删：委派 C1 管道，幂等
    @PostMapping("/{chunkId}/restore")        // 恢复：PG 复活 + 异步重嵌入
    // 租户守卫：jwt.getClaimAsString("owner") 空白 → IDENTITY_INCOMPLETE
}

// ChunkOpsService 异步重嵌入核心（从属副本失败仅告警，重建兜底）
private void reembedAndIndex(KbChunk chunk, KbDocument doc) {
    vectorStore.delete(List.of(chunk.getId()));                    // Milvus add 非 upsert，必须先删
    vectorStore.add(List.of(new Document(chunk.getId(), chunk.getContent(),
        DocumentEtlService.vectorMetadata(chunk, doc))));          // 元数据契约单一来源（坑位④ null 兜底）
    esIndexWriter.indexChunks(doc, List.of(chunk));                // ES 覆写（is_deleted 复位）
}
```

## 14.2 索引重建（4.5 定稿）

**端点**：`POST /api/v1/admin/rebuild`（body 缺省 / docIds 空 = 租户全量；指定 docIds =
目标增量）→ 返回 taskId 即受理；`GET /tasks`（租户域近 20 条 insertion order）/
`GET /tasks/{taskId}`（不存在与跨租户同返 REBUILD_TASK_NOT_FOUND）轮询进度。

**重建语义 = 文档级 reparse 编排复用**：kb-admin 不可依赖 kb-api，经
**`ReindexGateway` 依赖倒置**——接口定义在 kb-admin（`reparse(docId, tenantId, parseRoute)`
返回 `CompletableFuture<Boolean>`），实现 Bean `DocumentReindexGateway` 在 kb-api 委派
`DocumentService.reparse`（原子占用 + 蓝绿「全量写入 → diff 清理」+ version 递增全是
C1 既有语义，重建编排**零重复代码**）。reparse 的 ETL 进度回调 COMPLETED/FAILED
终态帧 complete(true/false)——即重建编排的汇聚点（replace 传不消费的空 future）。

**漂移修复收敛**：全量重建 = PG 事实源驱动——租户全部 SUCCESS + FAILED 文档
（FAILED 重入库是正当修复路径）逐个 reparse，存活 chunk 确定性同 ID 幂等覆写三库、
「旧有新无」经蓝绿 diff 精确清除。蓝绿 diff 仅覆盖 PG 新旧集，不清除「PG 已无行而
ES 残留」的历史孤儿——**每文档重建成功后追加 ES 孤儿清扫**：
`EsIndexWriter.findChunkIdsByDocId`（term doc_id 只取 _id，size 10000，失败返回空列表 =
清扫跳过不误删）查 ES 全集 − PG 现存集（含软删行——其 ES doc 带 is_deleted=true 标记
属合法存在）→ `deleteByChunkIds` 精确删（不走 deleteByDocId 全清，避免误删刚重写的
存活 doc）。**向量库孤儿不在本簇范围**：双向量库列表 API 异构（pgvector SQL /
Milvus query），产生条件仅「清理期向量删除失败」罕见路径，留离线清理（9.4 一致性
模型既定：PG 事实源，向量/ES 从属副本）。

**任务表形态（v2.36 Redis 化）**：`RebuildTaskStore` 接口 + `RedisRebuildTaskStore`
实现——键布局 `rag:rebuild-task:{taskId}`（RMap 状态，StringCodec）/
`:cnt:{succeeded|failed|skipped}`（RAtomicLong）/ `:failures`（RList 明细 JSON）/
`rag:rebuild-tasks:{tenantId}`（RDeque 租户索引，每租户 20 条 FIFO 淘汰并清键）；
TTL `rag.admin.rebuild.task-ttl-hours` 默认 24h——重启保留（窗口内）、跨实例轮询
共享（执行仍在受理实例）。任务状态 RUNNING→COMPLETED + total/succeeded/failed/
skipped 原子计数 + failures 明细（docId + reason）。Redis 故障：create/find/list
fail-closed `REBUILD_STORE_UNAVAILABLE`（HTTP 503），在途 record*/finish 告警不阻断。

**并发与超时**：滑动窗口 `rag.admin.rebuild.concurrency`（默认 4）——ETL 瓶颈在
embedding 批量调用（10 条/批供应商硬限制），窗口并发摊薄串行时延；单文档超时
`rag.admin.rebuild.doc-timeout-minutes`（默认 30，`orTimeout` 终态汇聚记 failed）。
目标文档前置校验（不存在/跨租户/处理中）记 skipped 不入窗口；gateway 同步异常
（占用竞态等）同记 skipped。

**实现期竞态修复**：已完成 future 的 `whenComplete` 先于 `pending.put` 执行，其内移除
为空操作，残留已完成条目使 `awaitAny` 空转死循环——定案为主循环统一
`drainCompleted(pending)`（removeIf isDone）出口。

**10 万 chunk 重建 <30min 验收论证**：重建时延由 embedding 吞吐主导（解析/切分为
CPU 侧次要项）——10 条/批 × DashScope 并发配额 × 窗口 4 文档并行，单 chunk 均摊
嵌入时延按百炼实测 ~0.3-0.5s/批 量级外推 ≈ 10 万 chunk ≤ 25min（不含网络抖动余量）；
E2E 以现语料（6 文档 168 chunk）全量重建实测单文档均时 × 线性外推 + 合成大文档
抽测校准（用户自测项）。

## 14.3 PromptTemplateManager

> **v2.29 复审定案**：PromptTemplateManager 自建否决，改 Git Ops 模板收编
> （任务 4.8：模板收编 yml/常量类，外部化率 100%）。以下为 v1 原草图存档。

```java
@Service
public class PromptTemplateManager {
    
    private final KbPromptTemplateRepository templateRepository;
    private final RedisTemplate<String, String> redisTemplate;
    
    private static final String CACHE_KEY_PREFIX = "prompt:template:";
    
    /**
     * 获取 Prompt 模板（Redis 缓存 → DB 回源）
     */
    public PromptTemplate getTemplate(String name, String version) {
        String cacheKey = CACHE_KEY_PREFIX + name + ":" + version;
        
        // 1. 尝试 Redis 缓存
        String cached = redisTemplate.opsForValue().get(cacheKey);
        if (cached != null) {
            return JsonUtils.fromJson(cached, PromptTemplate.class);
        }
        
        // 2. DB 回源
        KbPromptTemplateEntity entity = templateRepository
            .findByNameAndVersionAndStatus(name, version, "ACTIVE")
            .orElseThrow(() -> new ResourceNotFoundException("Prompt template not found"));
        
        PromptTemplate template = new PromptTemplate(entity.getTemplateText());
        
        // 3. 写入缓存（TTL 1小时）
        redisTemplate.opsForValue().set(cacheKey, JsonUtils.toJson(template), 
            Duration.ofHours(1));
        
        return template;
    }
    
    /**
     * A/B 测试：根据分组返回不同版本
     */
    public PromptTemplate getTemplateForABTest(String name, String abGroup) {
        KbPromptTemplateEntity entity = templateRepository
            .findByNameAndAbTestGroupAndStatus(name, abGroup, "AB_TESTING")
            .orElseGet(() -> templateRepository
                .findByNameAndStatusOrderByVersionDesc(name, "ACTIVE")
                .orElseThrow());
        return new PromptTemplate(entity.getTemplateText());
    }
}
```

## 14.4 Bad Case 运营闭环（4.7 定稿）

**工作流**（规划方案 N2 业界标准流程落地）：点踩反馈 → Bad Case 队列（审计行
feedback=NEGATIVE 即队列，自动）→ 根因标注（人工四分类）→ Golden Set 回灌
→ CI 复跑防回归。项目底座 3.17 已齐（kb_audit_log 全链路快照 + kb_feedback
期望回答 + audit_log_id 关联 + kb-eval 门禁），本簇补查询/标注界面与回灌通道。

**模块落位**：kb-admin（查询/标注/回灌/处理态四端点，BadCaseAdminController +
AuditLogQueryService + BadCaseService）+ kb-eval（回灌目标 = Golden 语料目录，
零代码变更）+ kb-domain（kb_audit_log.root_cause 新列 + 索引
(tenant_id, created_at DESC)；ddl-auto=validate，存量库先 ALTER）。

**端点**：
- `GET /api/v1/admin/audit-logs`——租户域审计多选项分页查询：from/to（ISO 闭区间）/
  userId/sessionId/feedback（POSITIVE/NEGATIVE）/status（SUCCESS/REJECTED/ERROR）/
  rootCause/annotated（true 已标注 / false 未标注），全部可选；默认 size 20 上限
  100；created_at 倒序。（v2.35：查询经 `AuditLogSpecs.search` 动态谓词执行，
  原 @Query 可选参数 PG 预编译缺陷修正，见章首注记。）视图附带 **feedbackExpectedAnswer**（页内 audit_log_id
  批量联查 kb_feedback，回灌对话框预填，N+1 防御）。
- `PUT /api/v1/admin/audit-logs/{id}/root-cause`——四分类标注：RETRIEVAL_MISS
  （检索未命中）/ REWRITE_DRIFT（改写漂移）/ HALLUCINATION（生成幻觉）/
  PARSING_GAP（解析不足）；非法值 INVALID_ROOT_CAUSE。
- `POST /api/v1/admin/badcase/reingest`——Golden 回灌（见下）。
- `PUT /api/v1/admin/feedback/{feedbackId}/resolved`——Bad Case 人工闭环标记，
  归属经 message→session 租户链校验（跨租户 FEEDBACK_NOT_FOUND 隐藏存在性）。

**守卫纪律（fail-closed）**：审计行不存在/跨租户一律 `AUDIT_LOG_NOT_FOUND`
（同 CHUNK_NOT_FOUND / MESSAGE_NOT_FOUND 不泄露存在性语义）；过滤枚举值非法
`INVALID_FILTER`、时间格式非法 `INVALID_TIME_FORMAT`（均 400）。

**Golden 回灌通道（Git Ops 形态）**：Golden Dataset 版本化管理在 Git
（kb-eval/src/main/resources/golden/，GoldenDatasetLoader 扫 classpath:golden/*.json），
回灌不建 DB 面——审计行转用例经 `rag.admin.golden.dir`（默认即 kb-eval 语料目录）
写 **badcase-qa.json**：id 确定性 `bc-{auditLogId}`（重复回灌 upsert 覆写，幂等），
question = 审计行 query_text（入库时已同款消毒），category 五选一（注入样本走
12.6 独立标注流程不收编），期望侧字段（expectedChunkIds/expectedDocs/
expectedAnswer/expectedKeywords）由运营人工判定填入、空则省略（加载器容忍缺失
跳对应指标，16.1 口径）。**人工 review 后 git commit，CI 复跑即消费**——回灌文件
与人工标注语料分文件共存，Git diff 天然隔离来源。成功副作用：关联反馈自动
resolved=true。目录缺失/不可写 GOLDEN_DIR_UNAVAILABLE、文件损坏 GOLDEN_FILE_CORRUPT。

**前端运维看板（4.9 定稿，v2.35 扩展）**：新页面 `/admin` 运维中心，四 Tab 一条工作流：
