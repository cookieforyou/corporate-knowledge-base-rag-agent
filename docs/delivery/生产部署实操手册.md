# 生产部署实操手册（本机打包 → ECS 容器化部署）

> 版本：1.5（2026-09-10 · 1.0 初版 / 1.1 增前端 §7 / 1.2 AppCDS 证伪退役——消费侧实测 SIGSEGV，§4 改判 + 现网恢复三步 + 训练服务移除 / 1.3 前端构建期 env 勘误——`VITE_AUTH_*` 构建期内联进产物，§7.2 补 `frontend/.env` 前置核对 / 1.4 CORS/WS 白名单补录——域名 https 访问后端判跨 origin，§7.4② 白名单追加 + 重建生效纪律 / **1.5 M1 前置核验**——§6.1 补监控四端口预检 + app compose CDS 注释残留清理）· 覆盖用户侧待执行项清单 **F3**（kb-api 容器化部署 + 前端 nginx 生产化）与 **M1**（监控栈生产部署 + 告警 14 条自检）· 高层口径（拓扑/资产/备份/安全）见[运维手册](./运维手册.md)，本手册专注**逐步可照做的操作序列**。
>
> **部署形态（本文档基准）**：本机（Mac）出 fat jar 与部署包 → 上传 ECS → ECS 上 `docker build`（免 Maven）→ `docker compose up`。ECS 2 核不做镜像内 Maven 构建；ECS 上**无需** Java/Maven 环境，只需 Docker。
>
> **约定**：所有命令按执行位置标注【本机】/【ECS】；`<...>` 尖括号占位符按实替换；ECS 部署目录钉 `/opt/kb-rag-agent`（systemd unit 的 WorkingDirectory 与此绑定，目录不同须同步改 unit）；compose 命令一律在 `infra/` 目录下执行（消费同目录 `.env`）。

## 0. 总览：一次完整部署的全流程

```
【本机】                                    【ECS /opt/kb-rag-agent】
┌───────────────────────┐                   ┌────────────────────────────┐
│ 1. mvn package 出 jar │ ── tar 部署包 ──▶ │ 4. 解压 + 配 .env          │
│ 2. 组装部署包(tar)    │     (scp)         │ 5. docker build（--no-mvn）│
│ 3. DEPLOY_VERSION     │                   │ 6. 停 fat jar → compose up │
└───────────────────────┘                   │ 7. 验证 healthy + 冒烟     │
                                            │ 8. 自愈 + systemd 开机自启 │
                                            │ 9. 监控栈 + 告警自检（M1） │
                                            │ 10. 前端部署（§7）         │
                                            └────────────────────────────┘
```

| 阶段 | 章节 | 预计耗时 | 备注 |
|---|---|---|---|
| 前置检查 | §1 | 10 min | 一次性；**切换前备份现网 env 是关键动作** |
| 本机构建组包 | §2 | 5-15 min | 机器性能决定 mvn 时长 |
| 上传与首次部署 | §3 | 30-45 min | 含切换窗口与功能冒烟 |
| AppCDS | §4 | — | **已证伪退役**（2026-09-10 消费侧实测 SIGSEGV；现网已训练者按 §4 三步恢复） |
| 自愈与开机自启 | §5 | 20 min | 含一次 reboot 验证 |
| 监控栈与告警自检 | §6 | 1.5-2 h | 六条真触发逐条做，可拆多次 |
| 前端生产部署 | §7 | 15 min | 宿主 nginx 托管 + 同源反代；**含 Casdoor 回调与 CORS/WS 白名单注册** |

**回滚兜底**（任何阶段失败均可退回 fat jar 直起形态，§3.8）：部署产物与配置相互独立，`docker compose down` 后按原命令直起旧 jar 即可，零破坏。

## 1. 前置检查【ECS】（一次性）

### 1.1 Docker 与磁盘

```bash
docker version --format '{{.Server.Version}}'      # 预期 ≥ 20.x
docker compose version                             # 预期 v2.x（"Docker Compose version v2.xx"）
df -h /                                            # 可用空间建议 ≥ 10G（镜像 ~400M + 卷 + 旧镜像留存）
free -h                                            # 记录总量，§3.3 内存限额校准用
```

### 1.2 存量基础设施盘点（应用依赖的五个服务）

```bash
docker ps --format 'table {{.Names}}\t{{.Image}}\t{{.Status}}\t{{.Ports}}'
ss -ltnp | grep -E ':(5432|9200|6379|9000|19530)\b'
```

预期：PG 宿主原生（`ss` 可见 5432）+ ES/Redis/MinIO/Milvus 容器各自宿主端口在监听。**容器内应用将经 `host.docker.internal`（= 宿主机网关）访问这些端口**——上表端口即为 `.env` 连接串应填的端口，与模板缺省（5432/9200/6379/9000/19530）不符的记下来，§3.3 改。

### 1.3 现网运行形态与 env 备份（⚠️ 最重要的一步）

现网 kb-api 以 fat jar 直起。**先找到它的启动 env 并备份**——这是新 `.env` 的抄值源（API key、特性开关都在里面）：

```bash
# 找到进程与启动命令
ps aux | grep -i 'kb-api.*jar' | grep -v grep
# 若 systemd 管理：systemctl cat kb-api（或你命名的 unit）看 ExecStart 与 EnvironmentFile
# 若手动 nohup：回忆/查 shell 历史（history | grep java）确认 env 文件路径
```

找到 env 来源后**完整备份**（例：env 是逐条 export 或一个文件）：

```bash
# env 文件形态（推荐先归一成一个文件再备份）：
cp <你的env文件> ~/kb-env-backup-$(date +%F).sh && chmod 600 ~/kb-env-backup-$(date +%F).sh
# 若只有运行中进程，可从 /proc 抓（PID 按上一步实值替换）：
tr '\0' '\n' < /proc/<PID>/environ | grep -E '^(DB_|ES_|REDIS_|MINIO_|KB_|JWT_|ZHIPU_|DASHSCOPE_|RAG_|DEEPSEEK_|RERANK_|TRACING_|LANGFUSE_|SPRING_|SERVER_)' > ~/kb-env-backup-$(date +%F).env
chmod 600 ~/kb-env-backup-*.env
cat ~/kb-env-backup-*.env    # 通读一遍，§3.3 逐键迁移用
```

### 1.4 现网健康基线（切换后对照）

```bash
curl -s localhost:8090/actuator/health          # {"status":"UP"}
# 前端正常登录 + 一轮带 [ref-N] 的对话，作为切换后冒烟的对照基线
```

## 2. 阶段一：本机构建与部署包组装【本机】

### 2.1 确认代码基线

```bash
cd <仓库根>
git pull                       # 或确认当前 HEAD 即你要部署的提交
git log --oneline -1           # 记下这个提交哈希（进镜像 tag，可追溯）
git status                     # 应干净（有本地改动先处理，勿带私货上生产）
```

### 2.2 构建 fat jar

```bash
mvn -q --no-transfer-progress -DskipTests package
ls -lh kb-api/target/kb-api-*.jar          # 预期一个 ~300-400M 的 fat jar（.jar.original 是中间件，忽略）
```

### 2.3 组装部署包

部署包 = 镜像构建三物（Dockerfile / docker-entrypoint.sh / fat jar）+ `infra/` 全树 + `DEPLOY_VERSION`（tag 事实源，ECS 上免 git/mvn 也能定 tag）。解压后与 `/opt/kb-rag-agent` 布局同构：

```
kb-deploy-*.tar.gz
├── Dockerfile                  # 镜像定义（根 .dockerignore 白名单收窄 build context）
├── docker-entrypoint.sh        # 容器入口（AppCDS 探测 + JAVA_OPTS）
├── DEPLOY_VERSION              # 镜像 tag（v{版本}-{git短哈希}）
└── infra/
    ├── .env.example            # Secrets 模板（ECS 上复制为 .env 填值）
    ├── docker-compose.app.yml  # 应用编排
    ├── docker-compose.monitoring.yml
    ├── kb-api.service / kb-monitoring.service
    ├── prometheus/  grafana/   # 监控配置与面板
    └── scripts/                # build-image / pg-backup / pg-restore-drill / neo4j-backup
```

命令序列（直接照做）：

```bash
cd <仓库根>
DEPLOY=/tmp/kb-deploy && rm -rf "$DEPLOY" && mkdir -p "$DEPLOY/kb-api/target"

# 三物 + infra 全树
cp Dockerfile docker-entrypoint.sh "$DEPLOY/"
cp kb-api/target/kb-api-*.jar "$DEPLOY/kb-api/target/"
cp -R infra "$DEPLOY/infra"
rm -f "$DEPLOY/infra/.env"    # 防御：本地误存的 .env 绝不上传

# tag 事实源（写入文件，ECS 侧 build --no-mvn 读它）
echo "v1.0.0-$(git rev-parse --short HEAD)" > "$DEPLOY/DEPLOY_VERSION"

# 打包 + 校验
PKG=/tmp/kb-deploy-$(date +%Y%m%d-%H%M).tar.gz
COPYFILE_DISABLE=1 tar -C "$DEPLOY" -czf "$PKG" .
ls -lh "$PKG"                  # 预期 ~350-450M（jar 占大头）
tar -tzf "$PKG" | head -20     # 抽验结构：首行应为 ./，见 Dockerfile / DEPLOY_VERSION / infra/ ...
```

> 前端 dist 不并入本包（独立打包独立发版，步骤见 §7.2——`infra/nginx/frontend.conf` 已随本包 infra/ 树带上）。

## 3. 阶段二：上传与首次部署（F3 主体）

### 3.1 上传与解压【ECS】

```bash
#【本机】上传（端口/账号按实换）
scp /tmp/kb-deploy-*.tar.gz <user>@<ECS_IP>:/tmp/

#【ECS】解压到部署根（覆盖式，与既有 git 仓库同名文件共存无冲突）
mkdir -p /opt/kb-rag-agent
tar -C /opt/kb-rag-agent -xzf /tmp/kb-deploy-*.tar.gz
ls /opt/kb-rag-agent           # 预期见 Dockerfile  docker-entrypoint.sh  DEPLOY_VERSION  infra  kb-api
cat /opt/kb-rag-agent/DEPLOY_VERSION    # 记住这个 tag，下下步要用
```

> `/opt/kb-rag-agent` 若已是现网 git 仓库目录：解压只新增 Dockerfile/entrypoint/jar/DEPLOY_VERSION 并覆盖 infra/（内容即仓库最新），git 仓库与其余源码不受影响——后续在 ECS 上跑 kb-eval 门禁等 Maven 活照旧。

### 3.2 配置 Secrets（`infra/.env`）【ECS】

```bash
cd /opt/kb-rag-agent/infra
cp .env.example .env && chmod 600 .env
vi .env    # 或你习惯的编辑器
```

**逐段填写口径**（模板已按 2026-09-10 修订对齐代码缺省，按下面三张表过一遍即可）：

**表 A · 必填实值**（全部来自 §1.3 备份的现网 env）：

| 键 | 说明 |
|---|---|
| `DB_USERNAME` / `DB_PASSWORD` | 现网 PG 凭据 |
| `ES_USERNAME` / `ES_PASSWORD` | 现网 ES 凭据 |
| `REDIS_PASSWORD` | 现网 Redis 凭据 |
| `MINIO_ACCESS_KEY` / `MINIO_SECRET_KEY` | 现网 MinIO 凭据 |
| `KB_MILVUS_USERNAME` / `KB_MILVUS_PASSWORD` | 现网 Milvus 凭据 |
| `JWT_ISSUER_URI` | Casdoor 签发地址（现网原值照抄） |
| `ZHIPU_API_KEY` | 主模型 GLM key |
| `DASHSCOPE_API_KEY` | 备用/Embedding/Rerank/图抽取共用 key |
| `GRAFANA_ADMIN_PASSWORD` | **新设强口令**（未设/留 CHANGE_ME 时监控栈拒绝启动，`:?` 守卫） |
| `KB_IMAGE_TAG` | §3.3 构建产出的 tag（先留占位，构建后回填） |

**表 B · 主机名改写（易踩的第一坑）**：现网 env 里所有 `127.0.0.1` / `localhost` 连接地址，容器内**必须**改为 `host.docker.internal`（compose `extra_hosts: host-gateway` 映射到宿主机）：

| 键 | 模板已给（核对端口与 §1.2 实际一致） |
|---|---|
| `DB_URL` | `jdbc:postgresql://host.docker.internal:5432/kb_rag_agent` |
| `ES_URIS` | `http://host.docker.internal:9200` |
| `REDIS_HOST` | `host.docker.internal` |
| `MINIO_ENDPOINT` | `http://host.docker.internal:9000` |
| `KB_MILVUS_HOST` | `host.docker.internal` |
| `NEO4J_URI` | `bolt+s://<bolt反代域名>:7687`（现网簇④形态原值——域名形态不变，勿改 host.docker.internal） |

**表 C · 现网已启用的特性开关（易踩的第二坑：漏配 = 功能静默丢失，无报错）**——对照 §1.3 备份 env，现网为 true 的在 `.env` 里**取消注释并置 true**：

| 键 | 影响 | 现网参考 |
|---|---|---|
| `RAG_GRAPH_ENABLED` | 图谱三路检索 + 抽取管道（簇④） | 启用中（需与 NEO4J_* 组同在） |
| `RAG_ORCHESTRATOR_ENABLED` | mode=agent 编排链（簇⑤） | 启用中 |
| `RAG_CACHE_ENABLED` | 语义缓存（簇③） | 按现网实况照抄 |
| `RAG_GUARDRAIL_RULES_SOURCE=db` | 词表 DB 单轨（模板已置 db，保持） | 已启用 |

其余保持模板缺省即可：`KB_MILVUS_COLLECTION=kb_chunks` / `KB_MILVUS_DATABASE=kb_rag_agent`（**勿改**——与现网实际集合/库一致，改错则检索恒空）、`RERANK_*` 注释态走内置百炼端点、`RAG_ROUTING_*` 缺省 GLM 主 + qwen3.8-flash 备、`TRACING_*` 缺省关、备份段（§7 DR1 用，先按模板）。

内存限额按 §1.1 `free -h` 校准：2 核小规格机器建议 `KB_API_MEM_LIMIT` 保持缺省 3G，`JAVA_OPTS=-Xms1g -Xmx2g` 保持——若 ECS 内存吃紧（存量容器 + PG 已占大半），两项同比例下调（如 2G / 512m-1536m）。

### 3.3 构建镜像【ECS】

```bash
cd /opt/kb-rag-agent
bash infra/scripts/build-image.sh --no-mvn
```

预期输出三段：`==> jar: kb-api/target/kb-api-...jar` → `docker build` 步骤（首次拉 eclipse-temurin:21-jre 基座 + apt 装 curl，1-3 分钟）→ 末行：

```
KB_IMAGE_TAG=v1.0.0-<短哈希>
```

回填 `.env`：

```bash
cd /opt/kb-rag-agent/infra
vi .env    # KB_IMAGE_TAG=v1.0.0-<短哈希>（与上一步输出一致；留 REPLACE_ME 会拒启）
```

### 3.4 干跑校验【ECS】

```bash
cd /opt/kb-rag-agent/infra
docker compose -f docker-compose.app.yml config --quiet && echo "compose 校验通过"
```

任何变量错（如 KB_IMAGE_TAG 未填）在此步即报错，先修再继续。

### 3.5 切换窗口：停 fat jar → 容器起【ECS】

> 选业务空窗执行。旧进程不停则 8090 端口冲突，新容器起不来。

```bash
# 1. 停现网 fat jar
ps aux | grep -i 'kb-api.*jar' | grep -v grep     # 找到 PID
kill <PID>                                        # 优雅停（~10s）；systemd 形态则 systemctl stop <unit>
ss -ltnp | grep 8090 || echo "8090 已释放"         # 确认端口让出

# 2. 起容器
cd /opt/kb-rag-agent/infra
docker compose -f docker-compose.app.yml up -d
docker compose -f docker-compose.app.yml ps        # STATUS: Up (health: starting)
```

**等待 healthy 的预期**：`start_period 90s` 内 healthcheck 显示 starting/health: starting 是**正常**——Spring Boot 全量装配 + Flyway 校验约需 30-60s。90s 后再 `ps` 一次，预期 `(healthy)`。未转 healthy：

```bash
docker logs kb-api 2>&1 | tail -50    # 看真实原因（连接拒绝=凭据/主机名；端口占用=旧进程没停干净）
```

### 3.6 启动核验【ECS】

```bash
curl -s localhost:8090/actuator/health             # {"status":"UP"}
docker logs kb-api 2>&1 | grep -iE 'flyway|started kb|migrating' | head -10
```

日志核验点（对照预期）：

| grep 关键行 | 预期 |
|---|---|
| Flyway 段 | 现网库已有 history（F1 已核验四行）——预期 `up to date`/`successfully validated`，**无新迁移**（V3 之后无 V4 时） |
| `Started KbRagAgentApplication` | 启动完成 |
| 装配行（图谱若启用） | `Neo4j Driver 已装配` + `图谱 Schema 幂等初始化完成` |
| 报错堆栈 | 应为零；`Bolt` 异常查 NEO4J_URI 是否照抄现网值 |

### 3.7 功能冒烟【你常用的浏览器】

1. 前端登录正常（Casdoor 回调不受影响，8090 未变、BACKEND_URL 无需动）；
2. 知识问答一轮：回答正常 + `[ref-N]` 引用可点（**检索通路 = Milvus 集合/库核对无误的实证**）；
3. 模式切 `agent` 问一轮（若现网启用编排——验证 `RAG_ORCHESTRATOR_ENABLED` 抄值无误，委派卡片正常）；
4. 文档管理列表可见既有文档（PG 通路）；上传一个小文档走到 SUCCESS（ETL + ES + 向量双写全通路）。

### 3.8 回滚预案（需要时）

```bash
cd /opt/kb-rag-agent/infra
docker compose -f docker-compose.app.yml down      # 容器栈整体退场（卷保留）
# 按原命令恢复 fat jar 直起（env 用 §1.3 备份文件）
```

镜像与卷不清除，随时可 `up -d` 再切回。

## 4. 阶段三：AppCDS —— 已证伪退役（2026-09-10 生产实测，勿再执行）

> **结论**：`--enable-preview` × AppCDS **消费侧不兼容（SIGSEGV）**——训练侧可成功写档（首轮实测 197MB `archive written OK`），但生产容器挂 `-XX:SharedArchiveFile` 启动后于 Hibernate 初始化期 `ConstantPool::klass_at_impl` 段错误，**崩溃循环**（连 error reporting 自身亦崩，`restart: unless-stopped` 反复拉起反复崩）。preview 字节码类入动态档案回放路径的 JVM 缺陷面（Temurin 21.0.11，坑位㊻ 19 章附录 E）。**CDS 训练服务与 entrypoint 消费逻辑已移除**（CDS 本为秒级启动加速非功能依赖，Dockerfile「失败即回落」设计预期兑现后整体退役）。
>
> **教训**：训练写档成功 ≠ 消费可行——兼容性结论必须以消费侧启动为准（首轮判读曾止于训练侧读数而误判「兼容性通过」，本轮勘误）。

**⚠️ 现网已训练过 app.jsa 的恢复**（旧镜像 entrypoint 仍会探测消费 → 崩溃循环，三步恢复）：

```bash
cd /opt/kb-rag-agent/infra
docker compose -f docker-compose.app.yml stop kb-api          # 1. 停崩溃循环
rm -f /var/lib/docker/volumes/infra_kb-cds/_data/app.jsa      # 2. 删档案（root；探测不到即回落普通启动）
docker compose -f docker-compose.app.yml rm -f kb-api \
  && docker compose -f docker-compose.app.yml up -d           # 3. 重建容器（顺带清崩溃期 core dump）并起
docker logs kb-api 2>&1 | grep '\[entrypoint\]'               # 预期：archive absent, plain startup
curl -s localhost:8090/actuator/health                        # {"status":"UP"} 服务恢复
```

（步骤 2 卷路径前缀 `infra_` = compose project 名即目录名；不确定先 `docker volume ls | grep kb-cds` 核对。新部署包含退役后 entrypoint（无探测逻辑），永不再触发。）

## 5. 阶段四：自愈验证与开机自启【ECS】

### 5.1 进程自愈

```bash
docker kill kb-api                                          # 模拟崩溃
docker compose -f docker-compose.app.yml ps                 # 30s 内自动拉起，随后回 (healthy)
```

### 5.2 systemd 开机自启

```bash
cp /opt/kb-rag-agent/infra/kb-api.service /etc/systemd/system/      # 目录非 /opt/kb-rag-agent 时先改 unit 内 WorkingDirectory
systemctl daemon-reload && systemctl enable --now kb-api
systemctl status kb-api        # active (exited)，RemainAfterExit 形态为正确
```

```bash
JWT='<Casdoor 令牌>'
for i in $(seq 1 25); do
  curl -s -X POST http://localhost:8090/api/v1/chat \
    -H "Authorization: Bearer $JWT" -H 'Content-Type: application/json' \
    -d '{"query":"自检查询'"$i"'","sessionId":"selfcheck-m1","mode":"rag"}' \
    -o /dev/null -w "%{http_code}\n"
done
```

**a) KbProcessRecentlyRestarted**：`docker restart kb-api` → 等约 1.5 分钟 → FIRING；uptime 满 5 分钟自动恢复。零配置改动。

**b) KbQuotaHitRateHigh**：`infra/.env` 增改 `RAG_RATELIMIT_RATE=2` → `docker compose -f docker-compose.app.yml up -d`（重建生效）→ 循环 25 次（多数 429 属正常）→ 命中率 >3% 持续 10 分钟 FIRING → **恢复**：删掉该行（或复原值）再 `up -d`。

**c) KbRejectionRateHigh**：运维中心第五 Tab（护栏词表）任选一条**注入侧 BLOCK 档**词项（红线纪律：本手册不写字面载荷，以系统内既有 BLOCK 词项原值构造）→ 循环 query 均含该词项跑 25 次 → 拒绝率 >15% 持续 10 分钟 FIRING。

**d) KbRequestErrorRateHigh**（⚠️ 主模型全失效模拟，窗口尽量短）：`.env` 改 `ZHIPU_API_KEY=invalid-drill` + `RAG_ROUTING_FALLBACK_ENABLED=false` → `up -d` → 循环 12 次（返回 ERROR 正常）→ 错误率 >5% 持续 5 分钟 FIRING → **立即恢复两项原值** `up -d`。

**e) KbRerankFallbackRateHigh**：`.env` 增 `RERANK_ENDPOINT=http://127.0.0.1:9`（不可达即降级）→ `up -d` → 循环 25 次 → 降级率 >10% 持续 10 分钟 FIRING → 恢复（删该行走缺省）`up -d`。

**f) KbEmptyRetrievalRateHigh**（窗口最长，建议最先发起与其他项并行孵化）：**空语料租户**（无文档的测试租户 JWT，或临时新建）循环 25 次 → 空检索率 >10% 持续 15 分钟 FIRING。

**可选加练**（不计入六条口径）：KbPrimaryModelDegraded——`.env` 仅改 `ZHIPU_API_KEY=invalid-drill` 而**保留** `RAG_ROUTING_FALLBACK_ENABLED=true` → `up -d` → 循环 8 次（前几次失败即切备用，回答仍正常返回）→ `:9090/alerts` 见 KbPrimaryModelDegraded FIRING + SLA 面板 OPEN 柱与接管速率抬升 → 恢复原值 `up -d`（30s 熔断窗口后 HALF_OPEN 试探回主）。该形态同时实证双供应商 SLA 链路。

> 每条涉及 `.env` 修改的，恢复后用 `docker compose -f docker-compose.app.yml ps` 确认 kb-api 回 healthy 再做下一条。b/c/e 每条约 10-15 分钟，全程含恢复约 1.5-2 小时，可拆多次执行。

### 7.4 Casdoor 回调与 CORS/WS 白名单注册（⚠️ 域名访问两项必做）

**① Casdoor Redirect URLs（不做则登录必败）**

登录跳转用 `window.location.origin + '/login'` 作 redirect URI——生产 origin 是新地址，须在 **Casdoor 控制台 → 应用 → Redirect URLs** 追加：

```
http://<ECS_IP>/login        # 域名访问则用域名；端口非 80 时带端口
```

既有本地调试地址（`http://localhost:5173/login`）保留不动。改完即生效（无需重启任何服务）。

**② CORS / WS 白名单（v1.4 补——同源反代 ≠ 免白名单；IP 直连 http 访问可跳过本项）**

- **机制**：浏览器对同源 **GET/HEAD 不发 `Origin` 头、同源 POST 会发**——这就是「文档列表/运维面板（GET）全正常、rag 问答与检索调试（POST）全 403 `Invalid CORS request`」症状分区的成因。后端收到 `Origin` 即做校验：**域名 https 访问时 TLS 在 nginx 前层终结、后端 Tomcat 视角 scheme 恒为 http**，同源比对必失败，落 CORS 白名单校验——白名单必须含生产 origin（`SecurityConfig` 既定设计：env 追加生产域；上传进度 WS 的 `WebSocketConfig` 同款白名单同改）。
- **操作**：`infra/.env` 两键**逗号追加**（带协议、无尾斜杠、协议按浏览器地址栏实际）：

  ```
  APP_CORS_ALLOWED_ORIGINS=http://localhost:5173,https://<你的域名>
  WS_ALLOWED_ORIGINS=http://localhost:5173,https://<你的域名>
  ```

- ⚠️ **生效形态 = 重建容器**：`docker compose -f docker-compose.app.yml up -d`——`docker compose restart` / `docker restart` **不重读 `.env`**（环境变量在容器创建时注入，restart 复用旧容器配置）。「改完 restart 仍 403」的第一嫌疑即此。
- **验证**：`docker exec kb-api printenv APP_CORS_ALLOWED_ORIGINS`（域名在列）→ 浏览器重发问答。仍 403 则 DevTools → Network 看 403 请求的 `Origin` 头与白名单条目**逐字比对**（www/裸域、协议、端口三看）。
